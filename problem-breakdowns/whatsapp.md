聊天消息有自己的身份，发送、投递与阅读是三个不同的事实。

## 遇见问题 · 先从一个具体场景开始

一对一聊天需要离线可收、重连可补齐。用户可能发送后立刻断网，也可能同时登录多台设备。


## 概念原理 · 先把概念讲清楚

- **消息ID**：标识一条逻辑消息，重试发送时保持不变，用于服务端与客户端去重。
- **设备游标**：某台设备已同步到的会话位置，不等同于用户已经阅读。


聊天主线先保证消息被持久接收，再尽力实时推送。在线连接降低投递延迟，持久历史让离线设备重连后补齐。界面上的“已发送”可以承诺服务端收下了消息，“已送达”需要设备确认，“已读”还要用户阅读信号。这些状态都不能仅根据发送者的网络连接推断。


同一会话的消息可由明确的顺序来源分配序号，设备按游标拉取缺口。不同会话通常无需全局排序。发送重试复用客户端消息ID，存储唯一约束防止重复插入；投递可能多次，客户端也按消息ID合并。消息身份、排序位置和设备进度各司其职。

路径：客户端消息ID → 去重插入 → 消息序号

基线设计 · 客户端稳定消息ID


### 基础架构 · 跑通一条主路径

实时连接加速投递，持久消息支持离线补齐。

路径：持久消息 → 在线推送或离线保留 → 设备

路径：会话排序 → 消息序号 → 设备游标

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

手机发送M后断网，服务端已保存但响应丢失。重连时手机重发同一个M，服务返回原消息状态，不新增气泡。接收方设备从序号50补拉51至55，即使实时通道已先收到55，也应去重并检查中间缺口，不能把网络到达顺序当提交顺序。

### 需求边界：“已发送”先承诺哪件事？

**备选：对方已经阅读**

阅读依赖接收端行为，发送接口不能提前保证。

路径：发送 → 假定已读 → 错误承诺

**基线：服务端已持久接收**

接收、投递、阅读是不同状态，界面需要区分。

路径：发送 → 持久接收 → 已发送

### 实体与接口：重试发送如何识别同一消息？

**基线：客户端稳定消息ID**

同一逻辑消息重试复用ID，数据库唯一约束防止重复存储。

路径：客户端消息ID → 去重插入 → 消息序号

**备选：每次到服务器都生成新身份**

新身份让服务无法判断这是重试还是第二条消息。

路径：重试 → 新ID → 重复消息

### 基础架构：离线用户靠什么收历史？

**备选：只向在线连接广播**

广播当时离线的用户无法收到内容。

路径：在线广播 → 用户离线 → 消息消失

**基线：消息持久化后异步投递**

实时连接加速投递，持久消息支持离线补齐。

路径：持久消息 → 在线推送或离线保留 → 设备

### 扩展瓶颈：如何保持房间内顺序？

**基线：会话内序号与游标**

会话序号提供稳定顺序，多设备按游标补齐；不要求所有会话全局排序。

路径：会话排序 → 消息序号 → 设备游标

**备选：依赖各设备本地时钟**

设备时钟不同且网络乱序，时间戳不足以表达提交序。

路径：设备时间 → 乱序到达 → 顺序分歧

### 故障处理：重连重复收到了上一条？

**备选：重复展示每次网络投递**

展示投递次数会让用户误以为真的发了多条。

路径：重连重投 → 直接展示 → 重复气泡

**基线：按消息ID去重后继续游标**

至少一次重投很常见，客户端与服务端都应区分消息身份和投递次数。

路径：重连补齐 → 消息去重 → 推进游标


## 适用边界 · 什么时候，需要重新考虑

多设备已读同步、群聊和端到端加密会增加设计层次，但不能由WebSocket自动提供。保留期与删除规则也影响补齐能力。先把持久接收和恢复讲清，再扩展复杂功能，避免“在线能聊”掩盖离线丢消息。


**本场景下的扩展方向**

会话内序号与游标。会话序号提供稳定顺序，多设备按游标补齐；不要求所有会话全局排序。

**另一条路径与它的代价**

依赖各设备本地时钟。设备时钟不同且网络乱序，时间戳不足以表达提交序。


## 带走结论 · 把这几个想法，带走

- 持久接收、投递与阅读是不同承诺。
- 稳定消息ID、会话序号与设备游标各有职责。
- 加密协议属于额外设计层，不能由WebSocket自动提供。
