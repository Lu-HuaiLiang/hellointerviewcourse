可播放视频是处理完成后发布的产物，原始字节只是流水线的起点。

## 遇见问题 · 先从一个具体场景开始

上传高清视频后，用户希望不同网络下都能播放。转码很耗时，观看流量远大于上传请求数。


## 概念原理 · 先把概念讲清楚

- **多码率版本**：同一视频按不同分辨率和码率生成的可播放输出，供不同网络条件选择。
- **播放清单**：描述可用版本和分段位置的元数据，播放器据此请求实际字节。


视频平台把控制路径与字节路径分开。应用维护视频ID、所有者和处理状态；对象存储保存原始文件与输出；转码Worker生成可分发格式；CDN承接大量观看流量。上传、转码和播放不应被一个长HTTP请求绑在一起，因为它们的耗时与扩展方式不同。


上传完成后任务进入队列，Worker生成多码率分段并验证完整性，最后发布清单并将视频标为可播放。使用版本化输出，可以让重试产物互不覆盖；只有完整的一组输出成为当前版本。播放器根据网络选择码率，但仍受授权、分段可用性与缓存命中的影响。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

一个用户上传大视频，接口先返回video_id并显示处理中。转码在生成第二个版本时失败，原始文件保留，清单没有对外发布。重试完成全部输出后原子切换清单，用户才能播放。此时播放从CDN获取分段，不再让应用服务逐字节转发同一热门视频给所有观看者。

### 需求边界：优先跑通哪两个行为？

**备选：先做个性化推荐**

推荐不是视频处理与播放的替代。

路径：推荐分数 → 候选视频 → 缺少播放资源

**基线：上传处理与按清晰度播放**

视频必须先变成可分发资源，推荐才有对象可推荐。

路径：上传 → 处理 → 播放

### 实体与接口：视频状态怎样表示？

**基线：上传中、处理中、可播放、失败**

状态区分接收字节和产出可播放格式，界面可以据此展示等待或失败。

路径：视频ID → 处理状态 → 可播放清单

**备选：拿到ID立即标可播放**

ID存在不说明转码已完成。

路径：视频ID → 立即播放 → 资源不存在

### 基础架构：转码放在哪条路径？

**备选：同步在上传接口转全部格式**

同步处理占住请求并容易在长任务中超时。

路径：上传HTTP → 长时间转码 → 网关超时

**基线：对象上传后队列调度转码**

Worker独立产出多个码率，完成清单指向已验证分段。

路径：对象存储 → 转码队列 → 多码率分段

### 扩展瓶颈：全球观看如何减轻源站？

**基线：CDN分发分段与清单**

分段可缓存，播放器按网络选择码率；动态授权仍在合适位置执行。

路径：播放器 → 附近CDN → 回源对象

**备选：所有播放直连源应用**

源应用将承受巨大出口带宽。

路径：全球播放器 → 单源应用 → 带宽拥塞

### 故障处理：一个转码任务重跑怎么办？

**备选：边写边让用户读取残缺文件**

半成品对外可见会造成播放失败。

路径：部分输出 → 提前可见 → 播放中断

**基线：版本化输出并原子发布清单**

任务可重试，只有完整验证的输出才成为当前版本。

路径：重跑任务 → 完整输出 → 发布清单


## 适用边界 · 什么时候，需要重新考虑

拿到ID、上传字节成功、转码完成和可以播放是不同边界。CDN也不能让未生成的分段突然可用。真实自适应码率还涉及带宽估计与缓冲策略，本实验只演示资源与发布状态，不模拟播放器算法或YouTube内部实现。


**本场景下的扩展方向**

CDN分发分段与清单。分段可缓存，播放器按网络选择码率；动态授权仍在合适位置执行。

**另一条路径与它的代价**

所有播放直连源应用。源应用将承受巨大出口带宽。


## 带走结论 · 把这几个想法，带走

- 元数据、转码任务与视频字节分离。
- 异步生成多码率分段，再通过CDN分发。
- 发布完整清单构成可播放状态的边界。
