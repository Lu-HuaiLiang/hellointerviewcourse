## 遇见问题 · 先从一个具体场景开始

构建文本对话产品。回答逐字流出，生成消耗昂贵算力，用户可能停止生成或在长对话中继续提问。


## 概念原理 · 先把概念讲清楚

- **生成任务**：一次模型推理请求的生命周期，连接中断后仍需确定是否继续、取消或已完成。
- **流式片段**：按顺序输出的部分结果，尚不等于完整回答或最终业务状态。


教学对话服务可分为会话存储、请求接入、推理调度与结果流。用户消息先获得稳定身份，生成请求进入受限资源池，再通过流式传输展示片段。模型执行耗时与资源消耗不确定，必须限定上下文、输出和并发预算，防止一个请求无界占用资源。


会话历史与生成任务分开记录，方便查询进行中、完成、取消和失败。网络断开不一定意味着生成停止，取消需要传到执行器并记录最终状态。重试应先确定原任务状态，避免重复生成和重复计费。部分输出可以保存，但应明确它是不完整回答。

### 实体与接口 · 把数据和接口连起来

核心实体：Conversation、Message、Generation、Usage。接口示例：POST /generations；POST /generations/{id}/cancel。一次生成关联输入、输出和状态，便于中断、重试和费用记录。

路径：消息 → generation_id → 输出与状态

基线设计 · 消息持久，生成有独立状态ID


### 基础架构 · 跑通一条主路径

流式降低用户感知的首字等待；仍要区分首token延迟与总完成时间。

路径：生成队列 → 推理Worker → 增量流

基线设计 · 排队调度后流式输出增量


### 扩展瓶颈 · 沿着瓶颈扩展

上下文与生成长度影响内存和计算，配额和批处理需要兼顾公平与延迟。

路径：token预算 → 公平队列 → 推理批次

基线设计 · 限制输入输出预算并公平排队


### 故障处理 · 处理不确定的结果

服务器传播取消，Worker协作停止并结算实际用量；断线策略与主动取消区分。

路径：取消请求 → Worker停止 → 部分结果状态

基线设计 · 独立取消信号并记录部分结果

### 从条件推到结果

用户收到前20个片段后网络断开。若服务继续生成并完成，重连可查询原任务结果；若协议支持续传，则按片段序号补齐，否则直接取完整保存结果。不能把重新打开连接一概当作新的生成意图，也不能将客户端没收到尾标记等同于任务未完成。

### 需求边界：首版范围先固定什么？

**备选：先训练完整基础模型**

训练算法不能替代会话、调度与生成状态管理。

路径：训练数据 → 模型训练 → 未定义产品链路

**基线：保存对话、流式生成、停止与配额**

本题设计推理服务产品链路，模型训练是独立的大范围课题。

路径：对话请求 → 推理服务 → 流式回答

### 实体与接口：消息和生成任务怎样区分？

**基线：消息持久，生成有独立状态ID**

一次生成关联输入、输出和状态，便于中断、重试和费用记录。

路径：消息 → generation_id → 输出与状态

**备选：把每个流片段当独立对话**

流片段只是传输增量，不能替代消息与任务身份。

路径：流片段 → 零散记录 → 无法恢复

### 基础架构：生成过程怎样展示？

**备选：等整篇生成完再开始传输**

整篇返回简单，但用户在长生成中看不到进展。

路径：推理全部完成 → 一次响应 → 长时间空白

**基线：排队调度后流式输出增量**

流式降低用户感知的首字等待；仍要区分首token延迟与总完成时间。

路径：生成队列 → 推理Worker → 增量流

### 扩展瓶颈：算力紧张时如何调度？

**基线：限制输入输出预算并公平排队**

上下文与生成长度影响内存和计算，配额和批处理需要兼顾公平与延迟。

路径：token预算 → 公平队列 → 推理批次

**备选：每个请求无限上下文和输出**

无限资源请求会挤占其他用户并造成过载。

路径：无限上下文 → 算力耗尽 → 其他用户饥饿

### 故障处理：停止生成或网络断开怎么办？

**备选：只关闭网页就假设GPU停止**

关闭显示通道不保证后端停止执行。

路径：页面关闭 → Worker继续 → 算力浪费

**基线：独立取消信号并记录部分结果**

服务器传播取消，Worker协作停止并结算实际用量；断线策略与主动取消区分。

路径：取消请求 → Worker停止 → 部分结果状态


## 适用边界 · 什么时候，需要重新考虑

流畅输出不证明内容正确，模型能力、检索授权和产品安全是独立层次。此处仅讨论通用对话式AI服务设计，不描述OpenAI或ChatGPT内部部署。成本估算也需基于实际模型与负载。


**本场景下的扩展方向**

限制输入输出预算并公平排队。上下文与生成长度影响内存和计算，配额和批处理需要兼顾公平与延迟。

**另一条路径与它的代价**

每个请求无限上下文和输出。无限资源请求会挤占其他用户并造成过载。


## 带走结论 · 把这几个想法，带走

- 本课是产品架构推演，不推断任何公司的内部实现。
- 消息、生成任务、流传输和算力调度分层。
- 上下文预算、取消、权限与用量记录要有明确边界。
