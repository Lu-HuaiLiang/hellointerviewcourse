# 在线拍卖：截止那一刻，谁赢了？

拍卖要把有效出价、截止与结算放进同一套可判定规则。

## 遇见问题 · 先从一个具体场景开始

竞价在截止时间前开放，最高有效出价获胜。请求会并发和重试，客户端时钟可能不准。


## 概念原理 · 先把概念讲清楚

- **有效出价**：经服务端检查价格、时间与资格后接受的出价，客户端发送不代表接受。
- **结算状态**：拍卖从开放转为结束后，记录胜者与后续处理的持久结果。


拍卖的关键状态是当前有效最高价及对应出价，而不是所有浏览者屏幕上的数字。展示可以异步推送，接受出价必须检查当前价格与拍卖是否仍开放。多个请求同时超过旧最高价时，应在同一拍卖边界内排序或条件更新，防止较低的新写覆盖较高出价。


截止由可信服务端规则判断，客户端倒计时只作展示。关闭拍卖与接受出价并发时，需要一个明确顺序：被接受在关闭之前的有效出价参与结算，之后拒绝。结算记录应幂等生成，通知、扣款等后续动作围绕同一拍卖结果执行。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

最高价100，A出110、B出120同时到达。若两者都读100后独立写回，A晚写可能把120覆盖成110。条件更新或串行处理保证检查最新状态。截止同时到达时也不能只比较客户端时钟，而要以服务端接受规则判定。

### 需求边界：先确定什么裁决依据？

**备选：用户设备显示的倒计时**

设备时间漂移或篡改会导致不公平裁决。

路径：设备时钟 → 各自截止 → 裁决不一

**基线：服务端接受顺序与截止规则**

截止和并列规则应由权威服务确定，客户端只是展示。

路径：服务端时间 → 截止校验 → 有效竞价

### 实体与接口：竞价记录需要什么？

**基线：唯一bid_id、金额、用户与拍卖**

历史用于去重、审计和争议处理；最高价是派生或受控状态。

路径：竞价记录 → 审计与去重 → 当前最高

**备选：只保存当前最高金额**

只有金额无法证明是谁何时出价，也无法区分重试。

路径：最高金额 → 无历史 → 无法核对

### 基础架构：并发更高出价怎么写？

**备选：先读价格再无条件覆盖**

较低的并发写入可能覆盖更高价格。

路径：读旧价 → 并发覆盖 → 价格倒退

**基线：原子比较价格与拍卖状态**

只在拍卖开放且新价满足条件时提交，同时记录竞价。

路径：条件竞价 → 原子更新 → 新最高价

### 扩展瓶颈：观众特别多怎么分发？

**基线：实时广播派生价格**

实时推送服务分担读取，竞价仍由权威路径确认。

路径：竞价提交 → 事件广播 → 观众

**备选：每人高频查询写库**

高频轮询和竞价事务竞争数据库资源。

路径：观众轮询 → 竞价主库 → 争抢资源

### 故障处理：关闭拍卖与出价同时发生？

**备选：由两个节点独立宣布成功**

独立判断可能产生两个胜者或截止后更新。

路径：竞价成功＋关闭成功 → 不同结果 → 争议

**基线：在同一顺序边界裁决**

关闭和接受竞价要按明确顺序处理，终态不可再被旧请求改写。

路径：竞价与关闭 → 顺序裁决 → 唯一胜者


## 适用边界 · 什么时候，需要重新考虑

“最高”还需要相同价格时的稳定规则，撤回、保证金和支付失败也需独立产品政策。这里的基线先确保出价排序与一次结算，不声称可直接覆盖所有拍卖法律或交易规则。


**本场景下的扩展方向**

实时广播派生价格。实时推送服务分担读取，竞价仍由权威路径确认。

**另一条路径与它的代价**

每人高频查询写库。高频轮询和竞价事务竞争数据库资源。


## 带走结论 · 把这几个想法，带走

- 拍卖是对一个热点状态的有序裁决。
- 服务端规则、审计记录与原子更新一起保证结果。
- 实时展示可以稍慢，最终胜者需要明确权威。
