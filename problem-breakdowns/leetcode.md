在线判题执行不受信任代码，隔离与资源预算先于吞吐优化。

## 遇见问题 · 先从一个具体场景开始

用户提交代码后获得运行结果。代码可能死循环、耗尽内存或访问网络；判题时间从几毫秒到几十秒不等。


## 概念原理 · 先把概念讲清楚

- **隔离执行器**：在受限制的执行环境中运行提交，约束文件、网络、进程与资源访问。
- **运行尝试**：某次任务执行的身份，与用户原始提交ID区分，便于重试和结果提交。


判题分成接收代码、排队调度、隔离运行和保存结果。API只负责创建提交与返回身份，不直接在业务进程执行用户代码。编译和运行都可能消耗大量资源或失败，因此需要明确CPU、内存、时间和输出大小限制。判题结果是对某套测试与运行环境的产物，应可追踪其版本。


任务由Worker按租约领取，在隔离环境里执行，再把结果提交到持久状态。外部监督器负责超时终止，不能期待死循环自行停止。一个用户的提交洪峰也需要配额、公平调度和语言环境池，防止占满其他用户的资源。执行、评分与展示可以异步连接。

### 从条件推到结果

### 需求边界：首要系统边界是什么？

**备选：让代码直接运行在API进程**

同进程执行会影响平台稳定性与数据安全。

路径：提交 → API进程执行 → 服务被拖垮

**基线：隔离不可信代码并限制资源**

隔离执行环境与业务服务，限制CPU、内存、时间和网络权限。

路径：提交 → 隔离执行器 → 受限运行

### 实体与接口：提交接口先返回什么？

**基线：submission_id和排队状态**

稳定提交ID让客户端查询异步进度，HTTP断开不会丢失任务身份。

路径：提交记录 → 队列 → 返回ID

**备选：一直保持请求直到跑完**

长连接容易超时，用户会不知道执行是否开始。

路径：HTTP等待 → 运行超时 → 状态不确定

### 基础架构：任务怎样领取？

**备选：从队列弹出后不留执行记录**

取走即删会在Worker宕机时丢失任务。

路径：弹出删除 → Worker崩溃 → 提交丢失

**基线：Worker租约领取并保存结果**

租约和持久状态让崩溃后可重投；结果按提交和运行版本提交。

路径：队列 → 租约Worker → 持久结果

### 扩展瓶颈：大量提交同时到达？

**基线：按语言池扩容并限制租户并发**

运行环境分池便于调度，配额和公平队列防止少数用户垄断。

路径：公平队列 → 语言执行池 → 资源配额

**备选：让一个用户无限占满机器**

无限并发损害其他用户的排队时间。

路径：单用户洪峰 → 全部Worker → 他人饥饿

### 故障处理：死循环或进程失控如何结束？

**备选：依赖用户代码主动退出**

恶意或错误代码不会可靠自我终止。

路径：死循环 → 等待自愿退出 → 无限占用

**基线：外部监督器超时终止隔离环境**

执行环境外部的限制才不依赖被测代码配合，终止后记录超时结果。

路径：时间上限 → 监督器终止 → 超时结果


## 适用边界 · 什么时候，需要重新考虑

隔离不是只加一个容器名称，真正的边界取决于运行时与权限配置。测试用例和平台密钥也不能暴露给提交。这里用状态路径解释原则，不提供可直接当生产沙箱的配置；实现时需要专门验证隔离能力。


**本场景下的扩展方向**

按语言池扩容并限制租户并发。运行环境分池便于调度，配额和公平队列防止少数用户垄断。

**另一条路径与它的代价**

让一个用户无限占满机器。无限并发损害其他用户的排队时间。


## 带走结论 · 把这几个想法，带走

- 隔离与资源限制是判题架构的核心。
- 提交、排队、运行、结果是可查询的状态。
- 重试、配额和环境清理决定平台是否稳定。
