协作编辑需要定义操作身份、位置与合并规则，不能只比较最终字符串。

## 遇见问题 · 先从一个具体场景开始

多人共同编辑同一文档，期望本地输入立即可见，断线后能恢复。文本位置会随其他人的操作改变。


## 概念原理 · 先把概念讲清楚

- **操作身份**：唯一标识一次编辑意图，使重投不会重复插入或删除。
- **收敛**：各参与者收到相同有效操作后得到一致状态，同时还需考虑是否保留编辑意图。


多人编辑在网络上会乱序、延迟和重投。若每次传整份文档并最后写入覆盖，用户会丢掉别人同时做的改动。操作级协议把插入、删除和属性变化作为对象，通过变换或有稳定身份的序列结构处理并发。OT与CRDT是不同家族，不能只把消息广播出去就称为完整合并算法。


客户端可以乐观显示本地编辑，再通过服务确认与合并收敛。服务保留操作日志与快照，使重连用户能补齐；操作版本或元素身份帮助解释“在什么位置插入”。文本序列还要处理并发删除、格式和撤销，单纯对字符串索引做加减只能解释最小例子。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

原文“AB”，两人同时在A后插入X与Y。各自本地看到AXB和AYB，交换操作后需要一致规则得到同一结果，例如AXYB。若两端都按自己收到的先后插入，就可能一端AXYB、另一端AYXB。稳定排序或操作变换解决的是这个具体歧义。

### 需求边界：先区分哪两种体验？

**备选：每次按键必须等所有用户确认**

等待全部用户会被慢网或离线成员阻塞。

路径：按键 → 等全部确认 → 输入卡顿

**基线：本地即时显示与全局收敛**

乐观本地编辑保持手感，再经合并协议收敛到同一文档。

路径：本地编辑 → 同步操作 → 收敛

### 实体与接口：操作应带哪类上下文？

**基线：文档身份、操作ID和基础版本**

基础版本说明位置所依据的文本，操作ID帮助去重。

路径：操作＋基础版本 → 变更上下文 → 可合并编辑

**备选：只发送当前光标数字**

位置5在另一个人插入后可能已不是原来的地方。

路径：光标位置 → 无版本 → 插入错位

### 基础架构：并发文本编辑怎样处理？

**备选：每次上传全文最后覆盖**

整篇覆盖会静默丢失其他人的文字修改。

路径：全文覆盖 → 并发写 → 丢失编辑

**基线：选择明确的OT或CRDT协议**

本教学路径采用中心排序与OT思路：按已提交并发操作转换位置；完整算法需系统验证。

路径：操作 → 中心排序与变换 → 广播新版本

### 扩展瓶颈：一个文档如何路由？

**基线：同文档到负责协调节点**

按文档分工简化单文档顺序；热点文档连接可另行分发。

路径：document_id → 协调节点 → 操作序列

**备选：操作随机发往独立节点各自排序**

独立排序会让副本对相同操作有不同次序。

路径：随机节点 → 各自序列 → 状态分歧

### 故障处理：离线很久重连怎么办？

**备选：无条件覆盖服务器最新全文**

旧全文覆盖会抹掉他人在离线期间的工作。

路径：离线旧全文 → 覆盖新文档 → 他人修改丢失

**基线：快照加后续日志并合并本地操作**

恢复到可用基线，再按协议处理本地未确认操作；历史不足需明确恢复策略。

路径：快照＋日志 → 本地操作合并 → 继续同步


## 适用边界 · 什么时候，需要重新考虑

收敛不自动意味着编辑意图完美保留，也不等于授权和审计。生产协作应使用经过验证的协议实现并测试复杂交错。这里是设计导学，操作路径不冒充完整OT或CRDT实现。


**本场景下的扩展方向**

同文档到负责协调节点。按文档分工简化单文档顺序；热点文档连接可另行分发。

**另一条路径与它的代价**

操作随机发往独立节点各自排序。独立排序会让副本对相同操作有不同次序。


## 带走结论 · 把这几个想法，带走

- 文本协作必须定义操作合并协议，长连接只是传输。
- 操作身份、版本与持久日志支撑重连与去重。
- 这里演示设计边界，不声称实现生产级OT或CRDT算法。
