支付最关键的失败不是明确拒绝，而是你不知道外部副作用是否已经发生。

## 遇见问题 · 先从一个具体场景开始

用户支付订单，支付服务商可能已经扣款却没有及时返回。用户点重试时，系统必须识别同一笔支付。


## 概念原理 · 先把概念讲清楚

- **逻辑支付身份**：标识一次付款意图，网络重试围绕同一身份继续。
- **对账**：将内部记录与外部确认事实核对，发现和修复遗漏、重复或状态分歧。


支付请求跨过外部服务后，超时无法区分未执行与执行后回执丢失。平台应先持久创建支付意图，记录金额、币种、订单与幂等身份，再调用渠道。返回给用户的状态区分处理中和最终结果，允许查询同一支付，不应建议直接创建另一笔付款来试一试。


渠道回调、主动查询与同步响应都可能更新同一状态。处理器需校验来源，按支付身份幂等应用，并避免旧通知覆盖新终态。内部业务更新与待发后续事件可用同一事务连接，外部动作则通过状态机恢复。账本记录应可追溯，不能仅保存一个可被随意覆盖的余额数字。


## 图解推导 · 从约束，一步步搭出基线

**需要保存的实体**

PaymentIntent、Attempt、ProviderEvent、Ledger

**对外接口示例**

POST /payments；GET /payments/{id}


### 需求边界 · 先划定边界

稳定身份贯穿本地记录、外部调用与回调，支持查询真实结果。

路径：支付意图 → 稳定身份 → 可查询状态

基线设计 · 同一业务支付有稳定身份且可核对


### 实体与接口 · 把数据和接口连起来

核心实体：PaymentIntent、Attempt、ProviderEvent、Ledger。接口示例：POST /payments；GET /payments/{id}。同键同参数返回已有结果，不同参数重用同键应拒绝。

路径：支付意图ID → 幂等记录 → 原结果

基线设计 · 同一支付意图复用幂等键


### 基础架构 · 跑通一条主路径

持久意图支持崩溃后核实，外部幂等键沿用同一身份；本地事务不能包住任意外部服务。

路径：持久意图 → 外部幂等调用 → 更新状态

基线设计 · 先持久意图再可靠调用与记录


### 扩展瓶颈 · 沿着瓶颈扩展

分区与异步提高处理容量，但幂等和账本不变量必须保留。

路径：支付ID路由 → 独立处理 → 受控账本

基线设计 · 按支付ID分工，账本约束不变


### 故障处理 · 处理不确定的结果

先核实已有支付，按事件身份和合法状态转移应用回调，对账修复遗漏。

路径：未知状态 → 查询与对账 → 确定终态

基线设计 · 状态查询、回调去重、周期对账


## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

支付P实际扣款成功，HTTP响应丢失。重试使用原幂等键或查询P，得到原结果；若每次新建ID，则渠道可能合法执行两次不同支付。稍后成功回调重复到达，也只应让订单确认一次，不能再次加购或发货。

### 需求边界：最先保证什么？

**备选：所有请求超时都立刻判失败**

超时只说明没等到响应，不能证明未扣款。

路径：响应超时 → 直接失败 → 可能重复扣款

**基线：同一业务支付有稳定身份且可核对**

稳定身份贯穿本地记录、外部调用与回调，支持查询真实结果。

路径：支付意图 → 稳定身份 → 可查询状态

### 实体与接口：客户端重试使用什么键？

**基线：同一支付意图复用幂等键**

同键同参数返回已有结果，不同参数重用同键应拒绝。

路径：支付意图ID → 幂等记录 → 原结果

**备选：每次请求创建新的支付意图**

新意图让服务商把重试看作新的合法扣款。

路径：每次新意图 → 多次扣款 → 重复支付

### 基础架构：调用服务商怎样与本地状态衔接？

**备选：只在内存记录调用状态**

崩溃后无法区分调用没发生还是已成功。

路径：内存状态 → 外部成功 → 崩溃失忆

**基线：先持久意图再可靠调用与记录**

持久意图支持崩溃后核实，外部幂等键沿用同一身份；本地事务不能包住任意外部服务。

路径：持久意图 → 外部幂等调用 → 更新状态

### 扩展瓶颈：订单量大如何扩展？

**基线：按支付ID分工，账本约束不变**

分区与异步提高处理容量，但幂等和账本不变量必须保留。

路径：支付ID路由 → 独立处理 → 受控账本

**备选：为了吞吐去掉唯一约束**

移除约束会让扩容同时放大重复记账。

路径：并行无约束 → 重复提交 → 账本冲突

### 故障处理：未知结果与重复回调怎么办？

**备选：超时就换一个新请求再次扣款**

新请求可能在第一笔已成功时再扣一次。

路径：超时新扣款 → 原扣款也成功 → 双扣

**基线：状态查询、回调去重、周期对账**

先核实已有支付，按事件身份和合法状态转移应用回调，对账修复遗漏。

路径：未知状态 → 查询与对账 → 确定终态


## 适用边界 · 什么时候，需要重新考虑

退款是新的业务动作，不是删除原付款事实。退款也有结果不确定与重复回执，需要自己的身份和状态。课程用于解释软件可靠性，实际金额精度、清结算和合规要求需由具体业务规范决定。


**本场景下的扩展方向**

按支付ID分工，账本约束不变。分区与异步提高处理容量，但幂等和账本不变量必须保留。

**另一条路径与它的代价**

为了吞吐去掉唯一约束。移除约束会让扩容同时放大重复记账。


## 带走结论 · 把这几个想法，带走

- 稳定业务身份比网络请求身份更重要。
- 已接受、处理中、成功、失败和未知要分开。
- 本地事务、外部幂等、回调与对账共同闭环。
