点击报表是事件事实的派生视图，实时数字与最终可核对结果要分开。

## 遇见问题 · 先从一个具体场景开始

广告点击需要按广告和分钟汇总供报表使用。事件可能重试投递、迟到或被修正；报表与最终结算的准确性要求应区分。


## 概念原理 · 先把概念讲清楚

- **事件身份**：稳定区分一次真实点击与其多次投递的ID，用于去重和追溯。
- **两级聚合**：先分摊局部计数，再按业务键汇总，缓解单热点键压力。


接收点击后先持久保存事件，再由流处理按广告与窗口聚合。原始事件是核对与重建依据，报表则是可修正视图。若仅在API进程内累加，重启会丢状态；若直接按收到次数加一，重试会抬高计数。先定义有效点击口径，计算才有业务意义。


事件时间确定所属窗口，去重身份区分重放。热点广告可加盐拆成多个局部桶，但最后必须按原广告键求和，并确保窗口与去重规则一致。迟到事件可能修正已输出值，最终冻结需要有明确期限；结算系统还需依据可审计事实核对。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

点击E在12:00发生，网络重投两次，第三次12:01才到。按投递次数得到3，按稳定事件身份应只有1；按接收窗口又可能把同一次点击拆到两分钟。正确流水线先辨认身份与发生时间，再更新对应窗口，报表展示修正后的计数。

### 需求边界：先分清哪两类结果？

**备选：所有即时数字都当最终账本**

未完成去重和迟到处理的即时数不适合直接当最终结算。

路径：即时计数 → 直接结算 → 误差固化

**基线：实时估计与可核对的最终结果**

即时结果允许迟到修正，最终结果依赖可追溯事实与对账口径。

路径：原始点击 → 实时聚合 → 核对结果

### 实体与接口：点击事件带什么关键字段？

**基线：event_id、ad_id、event_time**

事件身份支持去重，广告键分组，发生时间决定窗口。

路径：事件身份与时间 → 去重分窗 → 广告计数

**备选：只有广告名字**

名字不稳定，也无法可靠区分重复投递。

路径：广告名字 → 无事件身份 → 重复混入

### 基础架构：接收后怎样可靠处理？

**备选：只在API内存计数**

进程重启会丢失尚未保存的统计。

路径：点击 → 内存计数 → 重启丢失

**基线：持久日志后流式聚合**

持久日志把接收与聚合分离，崩溃可以重放，聚合状态需要检查点。

路径：点击 → 持久日志 → 窗口聚合

### 扩展瓶颈：一个广告极热怎么办？

**基线：两级聚合，先局部再按广告汇总**

热点可先加盐局部分摊，再二次汇总；窗口与去重边界需一致。

路径：热广告 → 局部桶 → 最终汇总

**备选：只增加不负责该键的Worker**

单键仍固定在一个Worker时，其他Worker空闲也无用。

路径：热键 → 同一Worker → 热点不变

### 故障处理：日志重放会不会多计？

**备选：每投递一次都累加**

投递次数不等于真实点击次数。

路径：重放 → 再次加一 → 虚高计数

**基线：按稳定事件身份去重与重建**

重放应产生等价结果；保留去重窗口与迟到期限，必要时离线对账。

路径：重放事件 → 去重状态 → 等价聚合


## 适用边界 · 什么时候，需要重新考虑

去重集合不能无限保留，期限必须覆盖约定重放与迟到窗口。超期限重放要走专门重建或核对路径。反作弊判断也不同于技术去重，稳定ID只能识别同一事件，不证明事件是真实有效用户行为。


**本场景下的扩展方向**

两级聚合，先局部再按广告汇总。热点可先加盐局部分摊，再二次汇总；窗口与去重边界需一致。

**另一条路径与它的代价**

只增加不负责该键的Worker。单键仍固定在一个Worker时，其他Worker空闲也无用。


## 带走结论 · 把这几个想法，带走

- 原始事件是可核对的事实，聚合是可重建的视图。
- 事件时间、去重期限和最终结果口径必须明确。
- 热点两级聚合增加了一层状态与协调成本。
