# 直播评论：热房间也要有界

原创中文教材，与网页使用同一份课程数据。

热门直播间把一个事件复制给大量连接，最慢用户不能决定整个系统的资源上限。

## 遇见问题 · 先从一个具体场景开始

一个直播间同时有很多观众。评论不断产生，手机网络速度不同；目标是及时看到新评论，并允许补看近期历史。


## 概念原理 · 先把概念讲清楚

- **分层扇出**：先把房间事件送到多个连接节点，再由节点分发给自己负责的观众。
- **有界缓冲**：为待发送数据设置上限，超过时按规则丢弃、断开或要求补拉。


直播评论包含持久接收、近期历史和在线分发。房间事件流可以按房间分组，但一个热门房间的观众连接不必全挤在同一进程。扇出节点共享上游事件，再分别服务一批用户，让连接数和出口带宽能够分担。


慢网络会让发送队列堆积。如果每个观众都无限缓存，少数慢连接就能拖垮服务器。必须定义有界策略：暂停、降采样、断开后按游标补拉，或者明确只保留最近窗口。显示层省略部分评论与持久层丢弃事实是不同语义，要让用户体验与存储承诺一致。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

房间每秒100条评论，某手机只能显示或接收20条，差额会持续累积。即使全局服务很快，这台设备也无法实时追上。可以只展示近期评论并提供补看入口，或断开后补拉历史；不能靠增加无限内存承诺它同时完整且即时看到全部内容。

### 需求边界：先承诺哪种体验？

**备选：所有观众每毫秒看到所有历史**

无限完整实时交付无法适应任意慢客户端。

路径：全历史实时推送 → 慢客户端 → 无限积压

**基线：实时新评论与近期补齐**

实时体验要区分新事件与历史查询，并说明积压时的降级。

路径：近期历史 → 实时流 → 游标补齐

### 实体与接口：评论怎样定位与排序？

**基线：room_id与房间内序号**

房间标识分组，序号支持去重与断线继续。

路径：房间ID → 评论序号 → 可继续位置

**备选：只有用户昵称**

昵称会变且不唯一，也不提供顺序。

路径：昵称 → 无稳定位置 → 无法补齐

### 基础架构：实时数据怎么送到观众？

**备选：每条都让观众扫描数据库**

频繁扫描把推送问题变成数据库洪峰。

路径：观众轮询全表 → 数据库 → 重复查询

**基线：持久接收后发布到订阅连接**

发布订阅扇出给连接服务，历史仍从持久存储查询。

路径：评论存储 → 房间发布 → 连接服务

### 扩展瓶颈：一个房间特别热怎么办？

**基线：分层扇出到多个连接节点**

同一房间事件复制到多个连接节点，各自服务一部分观众。

路径：房间流 → 扇出节点 → 观众分组

**备选：只给该房间一个连接进程**

单进程会受连接数和网络出口限制。

路径：房间流 → 单连接进程 → 出口瓶颈

### 故障处理：观众处理不过来怎么办？

**备选：为每人无限堆积内存**

无限缓冲可让一个慢客户端耗尽系统资源。

路径：慢观众 → 无限缓冲 → 内存耗尽

**基线：有界缓冲并提示补拉或降采样**

慢消费者策略控制内存，必要时断开后凭游标补拉，明确可能跳过的显示内容。

路径：慢观众 → 缓冲上限 → 补拉或降级


## 适用边界 · 什么时候，需要重新考虑

广播成功只说明发送流程进行过，不能证明每个观众都处理完成。序号、游标与保留窗口使重连有边界。删除与审核也要传播到历史和实时展示，不能仅在最初入库时检查一次。


**本场景下的扩展方向**

分层扇出到多个连接节点。同一房间事件复制到多个连接节点，各自服务一部分观众。

**另一条路径与它的代价**

只给该房间一个连接进程。单进程会受连接数和网络出口限制。


## 带走结论 · 把这几个想法，带走

- 连接推送与持久历史是两个系统能力。
- 热门房间需要分层扇出，慢观众需要背压。
- 序号与游标使重连恢复成为明确协议。
