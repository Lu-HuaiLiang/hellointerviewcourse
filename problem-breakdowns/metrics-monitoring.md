指标系统用可控维度压缩事件，必须防止观测数据本身无界增长。

## 遇见问题 · 先从一个具体场景开始

采集服务CPU、延迟与错误率，展示图表并触发告警。服务数量多，标签组合可能非常多；采集节点也会重启。


## 概念原理 · 先把概念讲清楚

- **时间序列**：指标名与一组标签值组合对应的一条随时间变化的样本序列。
- **标签基数**：不同标签组合的数量，决定索引和状态数量，而不只是单个标签长度。


指标适合回答聚合趋势，如每个服务的请求速率和错误比例；请求级详情更适合日志与追踪。采集、缓冲、写入和查询分层，时间分区与保留规则控制历史成本。若把每个request_id做标签，就把原本小规模聚合变成近似每请求一条序列，失去压缩意义。


查询按时间范围裁剪，长期数据可降采样，但平均值会隐藏短峰值。告警需要持续窗口、缺失数据策略和抑制规则，不能把采集失败直接当业务指标为零。监控系统本身也需要容量和失败观测，尤其在业务故障时往往会同时收到更大错误流量。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

100个服务、5种状态码类别、3个区域最多形成1500种组合；加入每天百万级唯一请求ID，序列数可能急剧增加。即使采样频率不变，管理序列元数据的成本也会膨胀。因此限制标签集合常比单纯降低采样频率更重要。

### 需求边界：先明确哪类数据？

**备选：把每个请求全文作为指标标签**

高基数与大标签会让索引和内存暴涨。

路径：每请求唯一标签 → 海量序列 → 资源耗尽

**基线：有界标签的指标与时间范围**

指标适合聚合观测，请求细节更适合日志或追踪。

路径：指标名＋有界标签 → 样本 → 时间查询

### 实体与接口：时间序列身份由什么决定？

**基线：指标名与完整标签集合**

标签组合区分服务、实例等序列，时间戳定位其中样本。

路径：指标＋标签 → 序列 → 时间样本

**备选：只由时间戳决定**

同一时间会有许多不同指标，不能混为一条。

路径：时间戳 → 混合全部指标 → 语义丢失

### 基础架构：存储查询主路径怎样组织？

**备选：永久全精度存到一张无索引表**

无限保留与全扫描成本会不断增长。

路径：所有样本 → 全表扫描 → 缓慢图表

**基线：时间分区、标签索引、分层保留**

近期高精度，远期聚合；查询先限定时间与标签。

路径：标签与时间 → 相关分区 → 聚合结果

### 扩展瓶颈：跨机器统计延迟P99怎么做？

**基线：合并兼容直方图后估计**

分位数不能简单平均；直方图桶可聚合，但精度受桶边界影响。

路径：各机直方图 → 桶合并 → 估计全局P99

**备选：对每台P99直接取平均**

平均局部分位数一般不等于全局分位数。

路径：各机P99 → 算平均 → 错误分位数

### 故障处理：指标没收到应视为什么？

**备选：自动当零错误率**

把缺失当零会在最需要告警时显示一切正常。

路径：缺失样本 → 填零错误 → 虚假健康

**基线：未知或失联，按规则处理**

缺样可能是采集故障，不是健康证据；告警持续时间和恢复规则要明确。

路径：缺失样本 → 失联检测 → 告警状态


## 适用边界 · 什么时候，需要重新考虑

缺失样本、计数器重置和真实零值需要区分。只保存每小时平均可能让10秒故障不可见。应为告警保留足够细粒度，为长期趋势保存聚合，并让指标维度有明确预算。


**本场景下的扩展方向**

合并兼容直方图后估计。分位数不能简单平均；直方图桶可聚合，但精度受桶边界影响。

**另一条路径与它的代价**

对每台P99直接取平均。平均局部分位数一般不等于全局分位数。


## 带走结论 · 把这几个想法，带走

- 控制标签基数，区分计数器、仪表和直方图。
- 时间分区与保留策略控制长期成本。
- 缺失不是零，局部分位数不能直接平均。
