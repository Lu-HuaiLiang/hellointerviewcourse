分布式缓存同时管理归属、容量与失效，缓存节点不是唯一事实来源。

## 遇见问题 · 先从一个具体场景开始

构建支持 get、put、TTL 的缓存。数据可从源站重建，内存有限，节点会增加或宕机。


## 概念原理 · 先把概念讲清楚

- **路由版本**：描述当前键归属规则的版本，帮助客户端与节点理解迁移中的位置。
- **热键复制**：让同一热点值有多个读取副本，区别于把不同键分到不同节点。


缓存集群需要回答键去哪找、找不到怎样回源、节点失效怎样退化。按一致性哈希路由可减少扩容时归属变化，但不会自动完成数据迁移或提供副本。缓存通常允许失去部分值后重建，关键是不能让大量同时回源压垮事实来源。


每个节点有限内存通过TTL和淘汰释放空间，热点与大键影响均衡。集群变化时客户端可能持有旧路由，可通过版本、重定向或兼容窗口处理。对热读可以增加副本或合并同键请求；对更新则需定义失效传播与允许旧值窗口。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

三节点缓存加入D，环上只有部分键改归属。即使迁移少，D初始没有值时仍会触发冷启动回源；若恰好接管热键，瞬时数据库负载可能很高。可以逐步切流、预热或合并在途读取，但必须根据热点分布判断，而非只看迁移键数量。

### 需求边界：先声明哪种数据承诺？

**备选：唯一且绝不丢失的业务账本**

账本需要不同的持久性与一致性设计。

路径：唯一账本 → 内存淘汰 → 事实丢失

**基线：可失效的加速副本**

明确可重建，才能合理选择淘汰与故障降级。

路径：读取 → 缓存副本 → 事实来源

### 实体与接口：条目除键值外需要什么？

**基线：到期时间与必要版本**

到期语义支撑TTL，版本可帮助防止旧更新覆盖新值。

路径：key＋value → expires_at → 版本检查

**备选：只有插入顺序**

插入顺序不足以判断有效期。

路径：插入顺序 → 无到期语义 → 陈旧数据

### 基础架构：成员变化时怎样路由？

**备选：随节点数改变直接取模**

取模简单，频繁扩缩容时大量键会改变位置。

路径：节点数改变 → 取模重算 → 大量重映射

**基线：一致性哈希配合成员版本**

环减少迁移范围，但客户端必须了解成员与迁移版本。

路径：键哈希 → 版本化环 → 负责节点

### 扩展瓶颈：一个键特别热怎么办？

**基线：热点复制或本地短缓存**

热点副本分散同键读取，需要控制更新与失效传播。

路径：热键 → 多个读副本 → 分担读取

**备选：只增加环上的虚拟节点**

虚拟节点分散区间，单热键仍可能集中。

路径：热键 → 更多虚拟点 → 同一负责节点

### 故障处理：节点死掉后请求大量未命中？

**备选：所有请求绕过源站保护**

无限回源将缓存容量问题放大为系统故障。

路径：故障节点 → 回源洪峰 → 源站超载

**基线：限流回源并逐步预热**

缓存故障不能把源站压垮，重建应控制并发。

路径：故障节点 → 有界回源 → 渐进预热


## 适用边界 · 什么时候，需要重新考虑

复制因子、持久化与一致性哈希是独立选择，不能互相替代。缓存命中成功也不证明值足够新。实验用固定哈希环展示归属变化，生产还需监控回源率、每节点负载和迁移期间错误。


**本场景下的扩展方向**

热点复制或本地短缓存。热点副本分散同键读取，需要控制更新与失效传播。

**另一条路径与它的代价**

只增加环上的虚拟节点。虚拟节点分散区间，单热键仍可能集中。


## 带走结论 · 把这几个想法，带走

- TTL、淘汰、路由与源站保护都是缓存API的一部分。
- 一致性哈希降低迁移扰动，不自动解决热键。
- 冗余与本地副本增加失效传播的复杂度。
