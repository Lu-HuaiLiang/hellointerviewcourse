棋局状态需要权威顺序，客户端负责交互显示而不是自行决定合法落子。

## 遇见问题 · 先从一个具体场景开始

两位玩家实时对弈，网络可能中断或重发落子。要求双方最终看到同一棋局与剩余时间；先不做棋力匹配算法。


## 概念原理 · 先把概念讲清楚

- **棋局版本**：每次有效走子后递增的位置标识，用于拒绝过时或重复操作。
- **权威状态**：服务端确认的棋盘、轮次和计时状态，客户端可显示预测但需服从确认。


一局棋是小规模共享状态，通常可以按棋局ID分配给明确的处理边界。走子请求携带棋局、操作身份与基版本，服务校验轮次和规则后更新。观众和对手收到事件，再更新显示。不同棋局可以并行，一局内部则需要明确先后，没必要让所有棋局全局串行。


网络断开后客户端重新查询快照或从版本补拉。重复提交同一走子不应再移动一次棋子。计时也要依据服务端规则计算，并区分网络等待政策，不能简单相信客户端剩余时间。落子确认与广播可以分开，广播失败不能抹掉已持久确认的走子。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

棋局版本18轮到白方。白方提交M，服务接受生成19，但响应丢失；重发M应返回原结果。另一请求仍带18则需要重新同步，不得在已经变化的棋盘上按旧位置执行。若对手已走到20，更需要快照或连续事件恢复。

### 需求边界：服务端最先守住什么？

**备选：完全相信客户端提交的棋盘**

客户端可篡改或落后，不能当唯一事实来源。

路径：客户端棋盘 → 直接覆盖 → 非法状态

**基线：合法落子、回合与权威时钟**

服务端验证状态，客户端可以预演但不能自行裁决胜负。

路径：落子请求 → 服务端规则 → 权威棋局

### 实体与接口：落子携带什么才能发现过期？

**基线：game_id、move_id、expected_ply**

预期回合序号识别旧请求，稳定ID处理重传。

路径：落子ID＋回合 → 版本检查 → 合法移动

**备选：只有起点和终点坐标**

同一坐标在不同棋局阶段可能含义不同。

路径：坐标 → 缺少回合 → 错误应用

### 基础架构：两边同时操作怎么处理？

**备选：任意节点各自更新棋盘**

独立更新可能形成双方都能走的分叉棋局。

路径：两个节点 → 各自棋盘 → 分叉

**基线：每局串行验证并持久记录**

同局形成顺序，检查轮次和规则，再广播确认状态。

路径：同局队列 → 合法性校验 → 持久落子

### 扩展瓶颈：很多独立棋局如何扩展？

**基线：按game_id分片协调**

棋局间通常独立，分片可并行推进，单局保持顺序。

路径：game_id路由 → 多个协调器 → 独立棋局

**备选：把所有棋局放一个全局锁**

全局锁让不相关的比赛相互等待。

路径：全部比赛 → 全局锁 → 串行等待

### 故障处理：玩家重连时怎样恢复？

**备选：信任断网前客户端剩余时间**

客户端时钟停住不代表比赛计时也暂停。

路径：旧设备状态 → 直接恢复 → 时间与棋盘分歧

**基线：权威快照加遗漏落子和时钟**

服务端给出当前基线和时间规则，重传旧落子按ID去重。

路径：重连 → 权威状态＋日志 → 一致棋盘


## 适用边界 · 什么时候，需要重新考虑

合法性校验、作弊检测和匹配评级是不同系统能力。服务器权威也不意味着界面必须每次都等网络才响应，可乐观显示并在拒绝后恢复。规则与计时政策要明确，不由动画完成时刻决定。


**本场景下的扩展方向**

按game_id分片协调。棋局间通常独立，分片可并行推进，单局保持顺序。

**另一条路径与它的代价**

把所有棋局放一个全局锁。全局锁让不相关的比赛相互等待。


## 带走结论 · 把这几个想法，带走

- 同一棋局需要权威状态与顺序，棋局之间可并行。
- 落子ID与回合版本分别解决重复与过期。
- 网络通道、业务规则和时钟裁决是不同层。
