## 遇见问题 · 先从一个具体场景开始

用户发布图片、关注作者、浏览动态。图片字节很大，动态列表只需要缩略图和少量元数据；私密账号限制可见范围。


## 概念原理 · 先把概念讲清楚

- **派生图片**：从原图生成的缩略图或不同尺寸版本，用于适配不同展示位置。
- **发布边界**：确认必要资源完整后让帖子对读者可见的时刻。


图片社区有上传、处理、发帖、时间线和图片分发多条路径。应用维护帖子和权限，原图与派生图保存为对象，CDN分发常见尺寸。时间线通常只引用帖子而非复制图片字节，这样关注者变多不会让每次发布把同一张图存数万份。


先完成对象上传与必要处理，再发布帖子，可避免时间线出现无法加载的半成品。删除或权限变化要传播到帖子、候选引用与缓存访问策略。热点内容的读取压力可以靠CDN与缓存分担，个性化时间线则需要独立候选与排序流程，不能把公共图片缓存套用到用户私有结果。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

原图10MB，列表只需小尺寸预览。若每位用户滚动列表都下载原图，带宽与等待都会放大；预生成缩略图后列表读取小对象，点开详情才取更清晰版本。生成失败时保留处理中状态或明确回退，不应发布一个永远指向缺失资源的地址。

### 需求边界：先跑通什么闭环？

**备选：先实现复杂滤镜编辑器**

滤镜不能替代服务端的媒体和动态链路。

路径：图片编辑 → 滤镜 → 没有发布链路

**基线：发布图片与浏览关注流**

发布和阅读决定存储、处理与分发，编辑器可作为后续客户端能力。

路径：上传 → 发布 → 关注流

### 实体与接口：Post里保存什么图片信息？

**基线：对象引用与各尺寸元数据**

元数据引用让派生动态轻量，图片由对象存储持有。

路径：Post元数据 → 媒体引用 → 对象存储

**备选：把原始图片塞进所有动态条目**

复制大字节到每条动态会放大存储与读取。

路径：动态条目 → 重复图片字节 → 存储放大

### 基础架构：图片如何准备给浏览使用？

**备选：读取时每次同步缩放原图**

每次现场处理会重复消耗CPU并增加延迟。

路径：每次浏览 → 下载原图 → 重复缩放

**基线：异步生成缩略图后发布可用状态**

预生成常用尺寸让高频读取更轻，处理状态避免显示残缺资源。

路径：上传对象 → 尺寸处理 → 可用媒体

### 扩展瓶颈：读多且作者粉丝差异大怎么办？

**基线：混合动态扇出加CDN**

普通作者预推，大作者读时合并，媒体通过CDN缓存。

路径：混合时间线 → 媒体CDN → 页面

**备选：所有粉丝都同步更新后才返回**

同步等待全体粉丝会让发帖延迟受最大粉丝数控制。

路径：发帖 → 同步写全部粉丝 → 长时间等待

### 故障处理：私密账号撤回访问权限？

**备选：永久公开图片URL**

公开长效地址会绕过之后的账号权限。

路径：公开永久URL → 绕过账号 → 私图可见

**基线：读取时授权并控制媒体凭证期限**

动态和媒体两条路径都要守权限，签名链接须限定范围和有效期。

路径：用户授权 → 短效媒体凭证 → 私密图片


## 适用边界 · 什么时候，需要重新考虑

对象存在不代表用户有权访问，猜不到URL也不是完整权限机制。图片版本、缓存期限和删除承诺需要一致。推荐算法可以继续深入，但先保证上传、发布和读取三条核心路径完整。


**本场景下的扩展方向**

混合动态扇出加CDN。普通作者预推，大作者读时合并，媒体通过CDN缓存。

**另一条路径与它的代价**

所有粉丝都同步更新后才返回。同步等待全体粉丝会让发帖延迟受最大粉丝数控制。


## 带走结论 · 把这几个想法，带走

- 图片字节、处理产物和社交元数据分离。
- 动态扇出与媒体分发优化不同资源。
- 私密内容的访问控制覆盖列表与对象地址。
