限流明确资源预算，突发容量和长期平均速率必须分别表达。

## 遇见问题 · 先从一个具体场景开始

API约定每个租户平均每秒10次，允许最多20次的短突发。多个网关同时接收同一租户的请求。


## 概念原理 · 先把概念讲清楚

- **令牌桶**：按速率补充令牌、最多保留桶容量，请求消耗令牌；允许有限突发。
- **原子扣减**：在同一受保护操作里检查额度并扣除，避免多个网关同时花掉相同余额。


限流器先定义维度：租户、用户、IP或接口，以及一笔请求消耗多少预算。全站限流保护总容量，租户限流保护公平性，二者可以叠加。令牌桶把允许的短突发与持续速度分开，比只统计今天总量更能控制瞬时压力。


多个入口共享一份配额时，分别读余额再写回会产生并发超放。共享存储的原子操作可保护桶状态，但每请求一次远程检查会增加延迟与热点。将有限令牌批量租给本地节点可以减少远程调用，代价是闲置浪费、精度和故障回收规则。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

桶容量20、每秒补10个令牌，初始满桶时可立刻通过20次单位请求；没有时间经过时第21次应被拒绝。1秒后最多补10个，而不是重新获得无限额度。两台网关若各持有独立完整桶，瞬间总共可放40次，已经改变了原来的租户承诺。

### 需求边界：先明确什么限流维度？

**备选：只按全站请求总数**

总量阈值可以保护全站，但不能提供租户公平性。

路径：所有租户 → 同一计数 → 相互挤占

**基线：租户配额与允许的突发**

租户维度防止一个客户吞掉别人配额，突发容量与平均速率分别定义。

路径：租户请求 → 租户桶 → 配额判断

### 实体与接口：令牌桶需要哪类状态？

**基线：剩余令牌与上次补充时间**

按经过时间补充令牌并限制桶容量，请求按成本消费。

路径：时间差 → 补充令牌 → 扣除成本

**备选：只记今天总访问量**

日总量不能表达每秒速率和短突发。

路径：日计数 → 无秒级约束 → 突发穿过

### 基础架构：多个网关共享配额怎样检查？

**备选：先各自读余额再分别写**

读改写分离会使配额被并发超花。

路径：并发读令牌 → 各自扣除 → 超放

**基线：原子检查并扣除共享桶**

原子操作防止多节点同时花同一批令牌；需统一时间与过期策略。

路径：网关集合 → 原子桶操作 → 允许或拒绝

### 扩展瓶颈：共享计数成为瓶颈？

**基线：有界本地租约分配令牌**

可批量授予本地令牌以减少远程调用，但全局精度、浪费与故障回收要定义。

路径：全局配额 → 分配有限租约 → 本地消费

**备选：每台都拥有完整租户配额**

独立完整配额会随网关数量倍增上限。

路径：每台完整额度 → 多个网关 → 配额倍增

### 故障处理：限流存储不可用时怎么办？

**备选：所有接口无条件永久放行**

失效开放不是所有业务都能承受的默认。

路径：存储故障 → 无限放行 → 下游过载

**基线：按业务风险明确放行或拒绝**

一般读取可选择临时放行，昂贵或关键操作可拒绝；策略必须预先说明并监控。

路径：存储故障 → 按风险策略 → 受控降级


## 适用边界 · 什么时候，需要重新考虑

时间计算要避免时钟回退制造令牌，失败时放行或拒绝要按业务风险预先定义。限流也不能证明下游请求安全或无重复副作用，它只是控制进入量。返回拒绝时应给调用方明确的等待与重试指引。


**本场景下的扩展方向**

有界本地租约分配令牌。可批量授予本地令牌以减少远程调用，但全局精度、浪费与故障回收要定义。

**另一条路径与它的代价**

每台都拥有完整租户配额。独立完整配额会随网关数量倍增上限。


## 带走结论 · 把这几个想法，带走

- 维度、补充速率、桶容量和请求成本要明确。
- 共享配额需要原子检查与扣除。
- 本地化能降延迟，但要说明精度和失败策略。
