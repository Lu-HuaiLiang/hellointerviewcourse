## 遇见问题 · 先从一个具体场景开始

搜索附近餐厅，按距离、评分和类别筛选。评论会更新，商户资料不频繁变化；先设计查询，不涉及个性化推荐。


## 概念原理 · 先把概念讲清楚

- **粗筛与精筛**：先用空间索引缩小区域，再计算距离并检查营业、类别和其他条件。
- **稳定分页**：在明确排序规则下继续取结果，避免热门分数变化导致重复或漏项。


本地搜索同时包含地理范围与文本或属性条件。空间编码可以快速找到候选商户，但网格边界不等于实际距离。用户站在边界旁时，街对面的商户可能属于另一个网格。因此先覆盖查询圆相交区域，再按统一距离模型过滤，才能兼顾成本与正确性。


排序可以结合距离、相关性、评分与营业状态，但这些数据的更新频率不同。地理位置较稳定，营业状态和评价会变化，预计算索引需要同步。候选缓存适合复用相近查询，但最终过滤仍要尊重当前资格；分页还应有唯一ID兜底排序，避免同分结果任意翻动。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

三公里半径覆盖4个网格，若只查用户所在格就漏掉部分近店；若把4格全部返回，又会包含圆外店铺。两阶段处理先保住召回，再去除多余候选。若筛选“营业中”后只剩3条，可以继续取候选补页，但应有工作上限。

### 需求边界：查询先固定哪些条件？

**备选：先追求全站评分总榜**

全站榜单无法直接回答附近有哪些餐厅。

路径：全站评分 → 总榜 → 远处商户

**基线：距离范围、类别与排序规则**

附近场景需要明确地理边界与排序，评分只是一个信号。

路径：位置与类别 → 候选 → 排序

### 实体与接口：评分数据怎样组织？

**基线：保留评论事实并维护聚合**

评论事实支持编辑、删除和重算，聚合让读取更轻。

路径：评论记录 → 聚合视图 → 评分

**备选：只存最终平均分**

只有平均数难以正确撤销某条评论贡献。

路径：平均分 → 无原始记录 → 无法重算

### 基础架构：附近搜索主路径怎样走？

**备选：每次扫描所有商户**

全扫描简单但随着数据增长会变慢。

路径：所有商户 → 全量距离 → 排序

**基线：空间粗筛再精确距离与类别过滤**

索引缩小候选，精确距离确保半径与边界正确。

路径：空间索引 → 精确过滤 → 候选列表

### 扩展瓶颈：热门区域读取很多怎么办？

**基线：缓存区域候选再按请求精筛**

区域复用减少碎片化，仍对具体坐标和权限过滤。

路径：区域缓存 → 请求距离过滤 → 结果

**备选：缓存每个经纬度的独立结果**

每个精确坐标都不同，命中率可能很低。

路径：精确坐标键 → 大量冷键 → 重复计算

### 故障处理：评论删除后聚合落后怎么办？

**备选：永远保留旧评分**

被删除内容继续影响评分会破坏数据含义。

路径：删除评论 → 旧聚合不变 → 评分失真

**基线：版本化修正并支持重算**

事件去重与修正恢复派生值，界面可说明刷新延迟。

路径：删除事件 → 聚合修正 → 新评分


## 适用边界 · 什么时候，需要重新考虑

格子越细并非越快：候选更少，却要查询更多区域。评价可信度也不是简单平均能解决，需要独立规则。课内原理针对地理与检索，不把教学评分当真实商户质量结论。


**本场景下的扩展方向**

缓存区域候选再按请求精筛。区域复用减少碎片化，仍对具体坐标和权限过滤。

**另一条路径与它的代价**

缓存每个经纬度的独立结果。每个精确坐标都不同，命中率可能很低。


## 带走结论 · 把这几个想法，带走

- 地理候选与精确距离分两步。
- 评分是派生视图，原始评论支持纠错重建。
- 缓存粒度要在命中率与精确性间选择。
