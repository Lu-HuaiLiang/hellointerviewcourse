找出附近司机是候选生成，承诺一趟行程还需要唯一有效的分配。

## 遇见问题 · 先从一个具体场景开始

乘客发起行程，司机不断上报位置。要求一名司机不能同时确认两张进行中的订单，位置允许短暂滞后。


## 概念原理 · 先把概念讲清楚

- **空间召回**：按位置范围找到可能合适的候选，再做距离、状态和资格过滤。
- **分配状态**：司机与行程的有效归属，必须防止并发确认导致重复占用。


高频位置更新与低频行程确认有不同要求。位置可以允许短暂滞后，带更新时间并通过空间索引查附近司机；真正接受订单时要重新检查可用状态，防止两个乘客同时拿到同一司机。将这两层分开，才能避免对每次位置变化都做昂贵强协调。


匹配可先召回候选并发送Offer，司机接受时用条件状态转移确认。行程、司机资格与超时要在明确边界内协调。位置最近不代表最快到达，也不代表仍空闲；路线估计、服务范围和用户取消都会影响最终决定。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

乘客P和Q都召回司机D。D先接受P，确认写入将D从空闲改为已分配；Q的接受检查失败，继续找其他候选。若P取消与D接受同时发生，行程版本决定谁先生效，失败方查询当前终态，而不是两边各自宣布成功。

### 需求边界：什么必须严格，什么可以稍旧？

**备选：所有位置与订单完全同强度**

所有高频位置强协调会显著增加延迟和成本。

路径：每次位置 → 全局强协调 → 高更新成本

**基线：行程归属严格，位置允许短暂旧**

将正确性预算放在不可重复分配的状态上，位置索引可以更轻。

路径：位置近似 → 候选 → 严格分配

### 实体与接口：位置数据如何建模？

**基线：司机最新位置与更新时间**

新鲜度用于剔除失联司机，历史轨迹可以另存。

路径：driver_id → 经纬度＋时间 → 空间索引

**备选：只保留司机注册城市**

城市无法支持附近查询与实时可用性。

路径：注册城市 → 粗位置 → 不可用候选

### 基础架构：匹配怎样走主流程？

**备选：找到最近司机就直接承诺**

最近司机可能正被另一个乘客分配。

路径：最近司机 → 直接承诺 → 双重分配

**基线：地理召回后原子确认分配**

召回只是候选，最终接受要检查司机与行程状态。

路径：附近候选 → 发送Offer → 原子确认

### 扩展瓶颈：位置更新很多怎么扩展？

**基线：按地域分区并设过期**

大多数请求只关心局部地域，分区与TTL控制工作和失效数据。

路径：地域分区 → 局部索引 → 过期清理

**备选：每次广播给所有乘客**

全局广播引入不必要的扇出。

路径：位置更新 → 全球广播 → 巨大扇出

### 故障处理：司机接受与乘客取消并发？

**备选：两个服务各自独立标成功**

双方都成功会造成司机赶来而乘客认为已取消。

路径：两处独立成功 → 状态分歧 → 无法履约

**基线：条件状态转移决定胜者**

对同一行程状态协调，失败方收到当前终态，重复事件幂等处理。

路径：接受与取消 → 状态版本检查 → 唯一有效状态


## 适用边界 · 什么时候，需要重新考虑

位置索引过期时需要剔除失联司机，不能把旧坐标当在线保证。跨地域调度、路线预测和公平分单可以继续深化，但不会替代最终归属约束。本课是候选与确认分层的设计推演。


**本场景下的扩展方向**

按地域分区并设过期。大多数请求只关心局部地域，分区与TTL控制工作和失效数据。

**另一条路径与它的代价**

每次广播给所有乘客。全局广播引入不必要的扇出。


## 带走结论 · 把这几个想法，带走

- 空间索引负责找候选，事务状态负责最终分配。
- 位置新鲜度和行程一致性采取不同策略。
- 接受、取消、超时都应进入同一状态机。
