候选推荐可以近似，双方互相喜欢产生关系则需要稳定且唯一的确认。

## 遇见问题 · 先从一个具体场景开始

展示附近候选，用户左右滑动，只有双方都喜欢才建立匹配。两个人可能几乎同时点赞。


## 概念原理 · 先把概念讲清楚

- **有向喜欢**：A喜欢B是一个方向明确的动作，不等同于B喜欢A。
- **匹配关系**：两个方向的喜欢均成立后生成的关系，应对同一对用户保持唯一身份。


匹配产品可以拆成候选发现与关系确认。候选根据位置、偏好和可见性筛选，允许一定更新延迟；喜欢与取消则是需要记录的用户动作。当双方都表达喜欢时生成匹配，必须防止并发触发两次创建和重复通知。把关系确认独立出来，才能明确约束。


可以用规范化用户对(min_id,max_id)作为关系唯一键，两个方向的喜欢保留各自状态。收到喜欢事件后检查反向状态，再通过唯一创建或事务建立匹配。只在内存检查“还没有匹配”是不够的，两台服务可能同时读到不存在。后续聊天权限应依据有效关系状态而非一条可能重复的通知。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

A和B几乎同时点喜欢，两次处理都发现互相喜欢。若各创建一个随机匹配ID，就会出现两个聊天入口；若关系记录以规范化用户对唯一约束保护，只有一条成立。通知使用匹配事件身份去重，双方看到一个稳定关系。

### 需求边界：先确定哪个匹配规则？

**备选：单向喜欢立即开放聊天**

单向开放是另一种产品规则，不能悄悄替换双向要求。

路径：A喜欢B → 直接聊天 → 无双向确认

**基线：双向喜欢才生成匹配**

双向条件确定匹配判断，聊天作为匹配后的功能。

路径：A喜欢B → B喜欢A → 生成匹配

### 实体与接口：匹配记录怎样去重？

**基线：规范化用户对作为唯一键**

将两人ID排序形成稳定用户对，唯一约束防止并发产生两份匹配。

路径：两人ID排序 → 唯一用户对 → 匹配记录

**备选：每次生成随机匹配ID**

随机ID不能识别两次创建属于同一对人。

路径：两次随机ID → 两条记录 → 重复匹配

### 基础架构：两人同时点赞，如何防错过匹配？

**备选：各自先读对方再写自己**

检查先于写入时，两边可能都判断尚未互赞。

路径：双方先检查 → 均不存在 → 匹配被漏掉

**基线：持久点赞并可靠触发双向检查**

先持久记录，再通过事务或可重试事件检查互惠关系，避免双方都读到不存在。

路径：保存喜欢 → 重试双向检查 → 唯一匹配

### 扩展瓶颈：附近候选怎样查？

**基线：空间粗筛后过滤已滑用户**

地理索引减少候选，再应用距离、偏好、屏蔽和已看条件。

路径：空间索引 → 偏好与已看过滤 → 候选

**备选：每次扫描全站用户**

扫描范围随用户增长，延迟和成本都上升。

路径：全站用户 → 全量计算距离 → 候选

### 故障处理：重复提交同一次滑动怎么办？

**备选：把重试当作另一份新喜欢**

重复写可能放大通知，也让撤销语义变乱。

路径：网络重试 → 重复动作 → 多次通知

**基线：稳定事件ID与状态去重**

每个动作具有稳定身份，重试不会制造重复通知或关系。

路径：重试滑动 → 去重 → 一次状态变化


## 适用边界 · 什么时候，需要重新考虑

位置与偏好召回不意味着一定有资格建立关系，屏蔽、撤销和账号状态要在确认或访问时检查。近似候选与严格关系可以有不同一致性预算，不能为了“实时推荐”把所有高频位置更新都强行纳入全局事务。


**本场景下的扩展方向**

空间粗筛后过滤已滑用户。地理索引减少候选，再应用距离、偏好、屏蔽和已看条件。

**另一条路径与它的代价**

每次扫描全站用户。扫描范围随用户增长，延迟和成本都上升。


## 带走结论 · 把这几个想法，带走

- 双向条件和唯一用户对保护匹配正确性。
- 匹配检查要能覆盖同时点赞的交错。
- 候选生成、关系判断与聊天属于不同路径。
