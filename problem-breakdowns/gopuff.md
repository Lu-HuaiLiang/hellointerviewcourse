即时配送要连接可卖库存、订单承诺与履约进度，而不是只有附近门店搜索。

## 遇见问题 · 先从一个具体场景开始

用户选择附近仓库的商品并下单。库存有限，支付和配送由不同服务完成；先保证不会因为重试创建多个订单。


## 概念原理 · 先把概念讲清楚

- **预留库存**：在订单确认期间暂时占用可售数量，避免其他订单再次承诺同一份货。
- **履约状态**：拣货、出库、配送和完成等阶段，每次转移要有可追踪的业务依据。


用户看到的库存可以是查询视图，确认购买时则需要对门店内真实可售资源作约束检查。附近门店不一定有货，有货也不一定能在承诺时间内送达。基线先划定门店服务范围，选定履约位置，再把订单与预留连接起来，避免订单确认后才发现资源没有归属。


库存预留、支付与配送跨越不同失败边界。先获得有期限的预留，再推进支付；支付结果不确定时查原操作，不能直接再扣一次。取消或超时释放预留也需要幂等身份，防止重复补回库存。履约过程中每一步都有持久状态，后台才能区分尚未执行与执行后回执丢失。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

某门店还有2盒牛奶，三个订单同时请求。确认路径只应让两份有效预留成功，第三份提示不足或换店。若第一单取消，释放的是它对应的一份预留，不能根据重复取消消息多次加库存。剩余数量是订单动作累积的结果，不是各服务随意维护的估计。

### 需求边界：先固定哪一组核心行为？

**备选：先实现全城最优路线算法**

最优路线很复杂，先做它不能保证用户能完成购买。

路径：全城路网 → 路线优化 → 调度计划

**基线：查附近库存、下单、查履约状态**

购物闭环决定所需数据；路线优化可在有实际订单后逐步深入。

路径：附近仓库 → 商品库存 → 订单状态

### 实体与接口：库存实体按什么区分？

**基线：商品与仓库的组合**

同一商品在不同仓库可用量不同，预留必须定位履约库存。

路径：商品＋仓库 → 库存记录 → 可预留量

**备选：只有商品编号**

全城总数不能证明某个附近仓库可发货。

路径：商品总量 → 任意仓库 → 可能缺货

### 基础架构：下单主流程怎样组织？

**备选：同时调用后直接返回完成**

并发调用节省等待，但没有状态协调会出现钱扣了货没有。

路径：并发扣款与扣库 → 部分成功 → 状态不明

**基线：预留、付款、确认状态机**

持久状态机跟踪进展；付款失败释放预留，完成才触发履约。

路径：订单 → 库存预留 → 付款确认 → 履约

### 扩展瓶颈：热门商品很多人购买？

**基线：按仓库原子预留并限流**

库存边界的原子更新保证正确性，限流减轻同一库存的竞争。

路径：请求限流 → 仓库库存条件更新 → 预留

**备选：只增加订单API实例**

应用扩容不能让同一份库存被多次合法预留。

路径：更多API → 同一库存行 → 竞争

### 故障处理：支付回调重复怎么办？

**备选：每次回调都新建配送单**

网络重试常见，重复创建会导致多次配送。

路径：重复回调 → 多张配送单 → 重复履约

**基线：按支付事件幂等推进**

检查已处理事件与订单状态，重复回调复用同一履约结果。

路径：重复回调 → 去重与状态检查 → 同一配送


## 适用边界 · 什么时候，需要重新考虑

展示库存可以允许短暂延迟，确认承诺不应依赖陈旧缓存。配送时间预测也不是事务保证，应与真实状态区分。重点是让库存、订单和履约各有事实来源与恢复动作，而非让一个巨型事务跨越全部外部系统。


**本场景下的扩展方向**

按仓库原子预留并限流。库存边界的原子更新保证正确性，限流减轻同一库存的竞争。

**另一条路径与它的代价**

只增加订单API实例。应用扩容不能让同一份库存被多次合法预留。


## 带走结论 · 把这几个想法，带走

- 库存可用性属于具体仓库，不是全站总数。
- 预留、支付与履约用状态机和补偿衔接。
- 每一段外部重试都要映射到稳定业务标识。
