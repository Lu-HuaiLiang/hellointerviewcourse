短码映射很简单，读写比例、唯一性与删除承诺让它成为系统设计题。

## 遇见问题 · 先从一个具体场景开始

设计可创建与跳转的短链接。假设链接创建后不修改，读取远多于创建；先不做点击统计，保留失效与下架能力。


## 概念原理 · 先把概念讲清楚

- **短码**：在服务命名空间内唯一标识目标地址的字符串，需要处理碰撞或分配冲突。
- **跳转响应**：向浏览器返回目标位置及状态语义；浏览器可能缓存结果，影响后续修改可见性。


短链接服务有两条主路径：创建时建立映射，访问时按短码找到目标并返回跳转。映射是事实，访问统计是附加事件。先保证创建与跳转可用，再决定统计是否允许异步和少量延迟；不要把每次跳转都绑到复杂分析流水线完成之后。


短码可以随机生成后依靠唯一约束检测碰撞并重试，也可由分配的数字编码产生。无论哪种方式，唯一性都要落实在存储或分配协议中。缓存适合热点跳转，但短链允许修改或删除时，需要重新确定缓存寿命和浏览器跳转缓存策略。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

假设每天100万次创建、1亿次跳转，粗看读写比100:1。可以先让映射写入数据库，热点读取走缓存，点击统计异步入日志。现在一个热点短链被删除：应用缓存清理后，浏览器之前长期缓存的跳转仍可能生效，因此删除承诺会反过来影响最初选择的跳转与缓存语义。

### 需求边界：先把什么功能做完整？

**备选：先做详细点击分析**

统计可以后续异步扩展，先做它会留下核心流程空缺。

路径：点击事件 → 分析系统 → 报表

**基线：创建与跳转**

创建保存映射，跳转查映射并返回重定向，构成最小闭环。

路径：创建链接 → 映射表 → 短码跳转

### 实体与接口：短码碰撞怎么处理？

**基线：唯一约束冲突后重试**

随机短码仍有碰撞概率，插入唯一键失败就重新生成；别覆盖旧链接。

路径：生成短码 → 唯一插入 → 返回链接

**备选：随机生成后直接覆盖**

省掉检测简单，但会让一个短码错误指向别人地址。

路径：随机短码 → 无条件覆盖 → 旧映射丢失

### 基础架构：需要保留下架控制，跳转先选什么？

**备选：永久301长期缓存**

永久缓存适合真正不可变公开资源，但客户端长期缓存会削弱下架控制。

路径：浏览器长期缓存 → 直接目标 → 绕过检查

**基线：302并控制缓存时间**

临时跳转与短缓存窗口更便于下架；服务端仍检查过期与授权策略。

路径：浏览器 → 跳转服务 → 302目标

### 扩展瓶颈：一个短码成为热点？

**基线：缓存映射并合并回源**

重复读同一映射适合缓存；失效时合并加载以保护源库。

路径：热门短码 → 缓存 → 未命中回源

**备选：只按短码加数据库分片**

分片分散不同键，但一个热短码仍落到同一片。

路径：热门短码 → 同一分片 → 热点持续

### 故障处理：缓存节点宕机，怎么办？

**备选：所有请求立即同时查库**

回源可恢复服务，但无限并发会把突发压力转移到数据库。

路径：缓存故障 → 回源洪峰 → 数据库排队

**基线：限速回源并重建**

控制并发能防止缓存故障演变为数据库故障，必要时短暂拒绝部分请求。

路径：缓存故障 → 有界回源 → 重建缓存


## 适用边界 · 什么时候，需要重新考虑

不要把编码当加密，连续短码可能被枚举。短链还要处理无效目标、过期与滥用，但这些策略需与核心映射区分。这里的基线不描述Bitly真实部署，重点是从读多写少推导缓存，从唯一身份推导冲突控制。


**本场景下的扩展方向**

缓存映射并合并回源。重复读同一映射适合缓存；失效时合并加载以保护源库。

**另一条路径与它的代价**

只按短码加数据库分片。分片分散不同键，但一个热短码仍落到同一片。


## 带走结论 · 把这几个想法，带走

- 唯一短码保护映射，重定向策略影响缓存与下架。
- 读多写少用缓存加速，但为失效保留受控回源。
- 点击分析与跳转主路径解耦，避免分析拖慢访问。
