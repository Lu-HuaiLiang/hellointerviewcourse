到期时间只决定任务何时具备资格，可靠执行还需要领取、重试与确认。

## 遇见问题 · 先从一个具体场景开始

用户安排未来某个时间运行任务，也可以取消。调度器可能宕机，执行任务的Worker也可能超时。


## 概念原理 · 先把概念讲清楚

- **调度与执行**：调度发现到期任务并分发，执行器实际运行工作，两者可独立扩展。
- **执行幂等键**：标识某任务的一次计划触发，例如任务ID与计划时间组合。


任务调度器需要持久保存下一次触发时间、任务参数和状态。扫描或时间分桶找到到期任务，再将执行交给Worker。调度进程重启不能丢掉计划，多实例同时发现同一到期项也不能导致无控制重复执行，因此领取和触发身份必须明确。


领取租约让失败后可恢复，但可能产生重叠执行。重复触发应复用同一计划实例ID，下游围绕它去重；周期任务的下一次触发则是不同身份。补执行、跳过错过周期或合并多次延迟触发，应事先约定，不能重启后无界补发。

路径：到期索引 → 原子领取 → 队列

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

每小时任务J在10:00到期，调度器发出后未记录确认就崩溃。恢复后再次发出的仍应是J/10:00，而不是一个全新随机任务。11:00触发使用J/11:00。区分计划任务与触发实例，才能既去掉重复，又不误删下一小时的合法执行。

### 需求边界：首版先定义哪个承诺？

**备选：任意外部副作用天然恰好一次**

没有外部事务配合就无法自动保证副作用仅一次。

路径：调度确认 → 假定仅一次 → 副作用风险

**基线：到期后至少一次调度，结果幂等**

调度与业务执行分开，可靠重投配合幂等来处理故障。

路径：到期任务 → 可靠投递 → 幂等执行

### 实体与接口：周期任务每次运行如何识别？

**基线：schedule_id加计划触发时间**

稳定运行标识区分不同周期并识别同次重投。

路径：计划ID＋触发时间 → run_id → 运行记录

**备选：只用调度器进程ID**

进程会重启，不能代表业务运行身份。

路径：进程ID → 重启变更 → 身份丢失

### 基础架构：调度器如何领取到期任务？

**备选：所有实例扫描后直接发送**

独立扫描会多次派发同一任务。

路径：多实例扫描 → 各自发送 → 重复派发

**基线：时间索引与原子租约领取**

索引定位到期范围，租约或条件更新防止正常情况下重复领取。

路径：到期索引 → 原子领取 → 队列

### 扩展瓶颈：调度量增长怎么办？

**基线：按时间桶与分片分工**

缩小每次扫描范围和实例负责集合，同时处理时钟偏差与过期补扫。

路径：时间桶 → 分片调度器 → 到期任务

**备选：让每个实例扫描全表**

全表扫描增加重复工作与数据库压力。

路径：所有实例 → 全表扫描 → 读放大

### 故障处理：取消与开始执行并发？

**备选：页面点取消就保证副作用撤回**

按钮无法撤回已经发出的邮件等外部结果。

路径：点击取消 → 承诺撤回 → 副作用已发生

**基线：定义状态转换与尽力取消边界**

未执行可阻止领取，已执行需要Worker配合；完成的副作用可能需补偿。

路径：取消请求 → 运行状态检查 → 取消或无法撤回


## 适用边界 · 什么时候，需要重新考虑

时间区间、时区、夏令时与系统时钟变化会影响周期规则。精确某时执行还受排队和资源限制，产品应区分“不早于”和“严格准时”。监控应看触发延迟与完成延迟，不能只看任务已进队列。


**本场景下的扩展方向**

按时间桶与分片分工。缩小每次扫描范围和实例负责集合，同时处理时钟偏差与过期补扫。

**另一条路径与它的代价**

让每个实例扫描全表。全表扫描增加重复工作与数据库压力。


## 带走结论 · 把这几个想法，带走

- 调度的时间准确度和执行语义要分别声明。
- 稳定run_id、租约与幂等支撑故障恢复。
- 取消不是回滚，周期任务也需要时区与错过触发策略。
