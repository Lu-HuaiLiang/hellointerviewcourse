## 遇见问题 · 先从一个具体场景开始

开票瞬间涌入大量用户。票有明确座位，付款需要时间；要求同一个座位最终只能卖给一个人。


## 概念原理 · 先把概念讲清楚

- **座位预留**：给购买者短时间占用特定座位的资格，与永久售出不同。
- **条件状态转移**：只允许从指定当前状态进入下一状态，例如可售→预留→已售。


座位是不可互换的独立资源，不能只用“剩余总数”代表谁拿到哪一张。浏览座位图可以走缓存，选座确认需要检查该座位当前状态并原子预留。把高流量浏览与较少的确认分开，能减少核心写路径压力，但不会取消唯一归属要求。


预留需要所有者、到期时间和版本。支付完成时必须确认预留仍属于该订单；超时释放与支付成功并发时，要有唯一有效的转移。队列或等待室可以削峰和控制入口公平性，但不能代替最终存储的条件检查。即使用户排到了前面，座位是否仍可售仍需确认。

## 动手探索 · 现在，亲手改变一个条件

先观察浏览和确认的边界，再运行两种库存模式。把故障放在预留到期与支付回执之间，解释为什么需要订单状态协同。

### 需求边界：最先写下哪条不变量？

**备选：所有用户必须瞬间成功**

有限座位不能满足每个请求，必须明确失败或排队。

路径：所有请求 → 无容量限制 → 承诺冲突

**基线：每个座位最多一个有效购买者**

座位唯一归属决定并发控制；浏览排队可以牺牲一点等待时间。

路径：用户请求 → 座位竞争 → 唯一购买者

### 实体与接口：预留需要记录什么？

**基线：座位、持有者、到期与状态**

服务端保存预留状态与期限，付款提交时再次校验有效归属。

路径：座位ID → 持有者与期限 → 预留状态

**备选：仅浏览器倒计时**

浏览器可关闭或修改，不能作为库存事实来源。

路径：浏览器计时 → 页面关闭 → 无人释放

### 基础架构：并发抢座位怎么提交？

**备选：各自读取空闲再无条件写**

两个请求可能同时读到空闲，随后互相覆盖。

路径：A读空闲＋B读空闲 → 各自写 → 双重承诺

**基线：原子条件更新空闲座位**

数据库原子转换空闲到预留，只有一个请求成功。

路径：空闲座位 → 原子预留 → 一个持有者

### 扩展瓶颈：热门演唱会怎么保护核心库？

**基线：等候室限速放行**

排队和缓存场次信息减轻核心竞争，放行也不等于保证有票。

路径：等候室 → 有界放行 → 座位事务

**备选：让浏览量全部直达写库**

浏览请求与库存事务抢资源会扩大故障。

路径：流量洪峰 → 库存写库 → 排队过载

### 故障处理：预留到期与支付成功同时发生？

**备选：只相信支付页面显示成功**

页面显示不能阻止后台同时把座位给别人。

路径：页面成功 → 过期已转售 → 重复出票

**基线：同一事务校验状态与归属**

明确状态转移，过期不再确认座位；钱已扣但无法出票需进入退款或核实流程。

路径：支付确认 → 状态与归属检查 → 出票或退款


## 适用边界 · 什么时候，需要重新考虑

到期不是由客户端倒计时单方面决定，服务端要用一致的时间与状态规则判断。若支付成功回执迟到且预留已释放，需要补偿或人工处理，不能偷偷重新占别人的座位。系统应公开中间状态并允许查询原订单。


**本场景下的扩展方向**

等候室限速放行。排队和缓存场次信息减轻核心竞争，放行也不等于保证有票。

**另一条路径与它的代价**

让浏览量全部直达写库。浏览请求与库存事务抢资源会扩大故障。


## 带走结论 · 把这几个想法，带走

- 座位归属必须在提交边界原子校验。
- 预留是有期限的状态，超时与付款需要协调。
- 等候室保护容量，不能替代库存一致性。
