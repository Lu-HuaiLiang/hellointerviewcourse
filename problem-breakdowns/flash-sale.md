秒杀先控制进入核心写路径的请求，再由原子规则确认有限库存。

## 遇见问题 · 先从一个具体场景开始

商品仅100件，开售时大量用户涌入。同一人可能反复点购买，付款异步完成；不能超卖，也不应因重试生成多份订单。


## 概念原理 · 先把概念讲清楚

- **准入**：在昂贵业务操作前限制进入量，减轻排队与资源争用。
- **库存预留凭据**：标识一次有效资源占用，后续付款、取消与释放都围绕它处理。


抢购流量远大于可售资源时，大多数请求注定不能成交。静态页面和商品浏览可以缓存，入口可限流与排队，核心路径只接受可承受数量的确认请求。即使已通过入口，也必须原子扣减或预留库存，不能把通过限流当作购买成功。


排队把到达速度变成等待，需要容量、超时和公平策略。确认成功后生成稳定订单与预留，付款异步完成；失败释放资源也要幂等。缓存库存可以提前挡住明显无货请求，但最终决定应由权威状态作出，缓存陈旧只能影响展示或拒绝效率，不能产生重复承诺。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

100件商品面对10万人，先让少量请求进入库存确认，最多创建100份有效预留。某份到期释放后才可能重新分配。若超时释放重复执行两次，就会凭空多出库存，因此“减库存要原子、加回去随便做”同样不成立。

### 需求边界：最先声明什么限制？

**备选：所有到达请求必须成功**

不能承诺超过供给的成功量。

路径：无限成功承诺 → 100件库存 → 不可满足

**基线：库存上限与每人购买规则**

有限库存决定会有失败，重复购买规则确定去重和资格校验。

路径：购买资格 → 有限库存 → 成功或售罄

### 实体与接口：订单去重范围怎么定？

**基线：活动、用户与业务请求身份**

按限购规则和稳定请求身份防止重复订单，数据库约束作为最终防线。

路径：活动＋用户＋请求 → 唯一约束 → 订单

**备选：每次点击都算全新购买**

用户网络重试不应消耗额外库存。

路径：重复点击 → 新订单 → 多次占库存

### 基础架构：库存扣减如何提交？

**备选：先查库存再无条件减一**

并发请求可能依据相同旧库存全部成功。

路径：读取100 → 并发无条件扣减 → 超卖

**基线：原子预留并持久记录状态**

检查与扣减同一步完成，预留记录用于付款、超时释放和核对。

路径：条件预留 → 订单状态 → 付款

### 扩展瓶颈：开售洪峰如何削减？

**基线：静态缓存、资格过滤、有界排队**

大部分浏览不必触及库存，写请求按下游能力放行，队列容量有上限。

路径：边缘缓存 → 资格限流 → 有界购买队列

**备选：全部请求直接写数据库**

数据库会把有限库存问题变成连接和锁的故障。

路径：所有流量 → 库存写库 → 过载

### 故障处理：付款晚于预留到期怎么办？

**备选：只要付过钱就再次扣库存**

原库存可能已给他人，再次确认会造成超卖。

路径：预留已释放 → 无条件确认 → 重复售卖

**基线：校验状态后确认或退款核实**

不能偷偷复活已释放预留，过期后支付需按业务规则退款或核实。

路径：迟到付款 → 预留校验 → 确认或退款


## 适用边界 · 什么时候，需要重新考虑

削峰不能创造库存或无限处理能力，前台应区分排队、预留、待付款与失败。异常热点、重试洪峰与机器故障都需要降级策略。本课库存实验只演示最小争用，排队公平与风控需要独立实现。


**本场景下的扩展方向**

静态缓存、资格过滤、有界排队。大部分浏览不必触及库存，写请求按下游能力放行，队列容量有上限。

**另一条路径与它的代价**

全部请求直接写数据库。数据库会把有限库存问题变成连接和锁的故障。


## 带走结论 · 把这几个想法，带走

- 限流控制到达速度，原子库存控制正确性。
- 排队成功不等于购买成功，付款成功也需匹配有效预留。
- 用同一订单状态机衔接重试、支付与过期。
