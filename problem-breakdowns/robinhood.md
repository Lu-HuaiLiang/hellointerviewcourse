行情展示与订单处理共享用户界面，却有不同的数据承诺和恢复要求。

## 遇见问题 · 先从一个具体场景开始

设计零售证券交易的系统骨架：展示行情、提交订单、查询成交与账户。行情持续变化，订单可能只成交一部分；每次状态变化都需要可追踪。


## 概念原理 · 先把概念讲清楚

- **订单生命周期**：已接收、待路由、已确认、部分成交、成交或取消等业务阶段。
- **成交事件**：改变持仓与资金记录的事实，需要稳定身份并可核对来源。


教学交易平台可分为行情流和订单流。行情强调及时分发，可根据产品规则合并中间更新；订单强调稳定身份、状态查询与重复保护。用户点提交后，平台接收并不等于外部市场已成交，界面必须保留处理中等中间态，不能因一次成功响应就立即显示最终持仓。


订单意图先持久记录，再路由外部执行，回执与成交更新驱动状态机。网络超时要查询原订单而不是创建新订单。成交事件去重后更新账本或持仓，部分成交与撤单并发需要根据确认顺序处理。展示缓存可以重建，资金事实则需要可追溯记录。

订单与账本保护业务事实，行情流是高频读取路径，可独立扩展。

路径：行情流 → 报价界面 → 独立下单

基线设计 · 订单与资金，行情单独分发


### 实体与接口 · 把数据和接口连起来

核心实体：Account、Order、Execution、LedgerEntry。接口示例：POST /orders；GET /orders/{id}。订单可未成交、部分成交或撤销，成交事件逐笔更新账本与剩余量。

路径：订单 → 多笔成交 → 账本

基线设计 · 订单表达意图，成交可能有多笔


### 基础架构 · 跑通一条主路径

先持久业务身份与风险检查，之后可靠路由；不能因本地崩溃失去外部订单关联。

路径：校验与预留 → 持久订单 → 外部路由

基线设计 · 认证校验、资金预留、持久订单


### 扩展瓶颈 · 沿着瓶颈扩展

独立行情通道减轻账本与订单存储压力。

路径：行情源 → 订阅扇出 → 客户端

基线设计 · 行情订阅分层扇出


### 故障处理 · 处理不确定的结果

稳定成交身份与状态版本避免双计，定期与外部对账发现遗漏。

路径：成交回报 → 去重与对账 → 持仓账本

基线设计 · 按execution_id去重并核对累计量

### 从条件推到结果

订单O买10单位，收到成交4单位后用户取消剩余6单位。撤单请求在途期间又成交2单位，最终可能是成交6、取消4。不能把“点击取消”当成交事实被回滚，也不能让迟到回执把已经发生的成交抹掉。

### 需求边界：哪里需要更严格的状态控制？

**备选：所有行情跳动都写账户事务**

把行情和交易事务混在一起会扩大争用。

路径：行情更新 → 账户事务 → 热点竞争

**基线：订单与资金，行情单独分发**

订单与账本保护业务事实，行情流是高频读取路径，可独立扩展。

路径：行情流 → 报价界面 → 独立下单

### 实体与接口：订单和成交记录如何区分？

**基线：订单表达意图，成交可能有多笔**

订单可未成交、部分成交或撤销，成交事件逐笔更新账本与剩余量。

路径：订单 → 多笔成交 → 账本

**备选：提交订单立即视为全额成交**

提交只代表接受意图，不能承诺市场已匹配。

路径：订单提交 → 全额成交标记 → 虚假持仓

### 基础架构：请求进入交易路径先做什么？

**备选：先发给外部场所再想怎么记录**

外部已经收到而本地没记录，会形成难以核对的订单。

路径：外部发送 → 本地崩溃 → 未知订单

**基线：认证校验、资金预留、持久订单**

先持久业务身份与风险检查，之后可靠路由；不能因本地崩溃失去外部订单关联。

路径：校验与预留 → 持久订单 → 外部路由

### 扩展瓶颈：大量用户看同一行情怎么扩展？

**基线：行情订阅分层扇出**

独立行情通道减轻账本与订单存储压力。

路径：行情源 → 订阅扇出 → 客户端

**备选：每人不断轮询交易主库**

行情观看不应与资金事务竞争主库。

路径：全部行情读取 → 交易主库 → 吞吐竞争

### 故障处理：成交回报重复或乱序怎么办？

**备选：每收到回报就增加持仓**

投递次数不等于实际成交次数。

路径：重复回报 → 重复记账 → 错误持仓

**基线：按execution_id去重并核对累计量**

稳定成交身份与状态版本避免双计，定期与外部对账发现遗漏。

路径：成交回报 → 去重与对账 → 持仓账本


## 适用边界 · 什么时候，需要重新考虑

本课只讨论软件状态与事件处理，不提供交易策略。真实接入还受市场、清算和业务规则约束，不能用简化状态图替代。行情旧值与订单状态不确定应分别展示，避免用户误以为系统已完成操作。


**本场景下的扩展方向**

行情订阅分层扇出。独立行情通道减轻账本与订单存储压力。

**另一条路径与它的代价**

每人不断轮询交易主库。行情观看不应与资金事务竞争主库。


## 带走结论 · 把这几个想法，带走

- 订单意图、成交事实与资金账本是不同实体。
- 高频行情分发与严格交易路径分离。
- 外部状态不确定时查询与对账，不猜测成功或失败。
