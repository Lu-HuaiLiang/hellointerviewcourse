# 文件同步：先传字节，再发布版本

原创中文教材，与网页使用同一份课程数据。

同步不是把文件复制过去，而是让设备围绕同一个版本历史达成可恢复的理解。

## 遇见问题 · 先从一个具体场景开始

多设备上传和下载大文件，网络可能中断，两台设备也可能同时修改。要求不发布残缺文件，并能发现版本冲突。


## 概念原理 · 先把概念讲清楚

- **文件版本**：某次完整内容的稳定身份，发布后应能区分于其他修改。
- **同步游标**：设备已看到的变更位置，用于发现断线期间发生的新增、修改和删除。


文件同步包含字节传输与版本协调。先上传分段并验证完整，再在元数据里发布新版本；设备根据变更日志更新本地状态。把版本从文件路径中分离，可以让两个相同路径的不同内容不互相混淆，也能让失败重试围绕已有上传会话继续。


并发修改需要冲突策略。如果A和B都基于版本7修改，A先发布8，B提交时应发现基版本已变化。系统可以创建冲突副本、要求合并或按明确规则处理，不能把最后到达的字节悄悄当成唯一历史。删除同样是需要传播的变更，不只是让某台设备文件消失。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

A离线修改报告，B在线修改同一路径并发布新版。A重连携带旧基版本，服务保留两份内容并显示冲突，用户再决定如何合并。若只比较设备时钟，大幅偏差会让旧内容覆盖新内容。版本身份与服务器确认顺序比“文件修改时间看起来较晚”更可靠。

### 需求边界：首版优先保证什么？

**备选：先支持在线多人编辑**

多人编辑会引入操作合并，超出可靠文件同步的基础边界。

路径：编辑操作 → 合并协议 → 协作状态

**基线：可靠上传下载和版本**

同步首先要完整传输与跟踪版本；文本协同是另一层冲突模型。

路径：设备 → 完整上传 → 版本发布

### 实体与接口：两个设备都从v1修改，怎样提交？

**基线：带base_version条件提交**

比较基础版本，冲突时保留冲突副本或显式合并，避免静默丢掉修改。

路径：base_version → 版本检查 → 提交或冲突

**备选：最后上传覆盖全部**

最后覆盖易实现，但不满足发现并发冲突的要求。

路径：设备A与B → 无条件覆盖 → 一份修改丢失

### 基础架构：2GB文件怎样传输？

**备选：全部经过应用服务器**

代理全部字节可集中控制，但增加应用带宽与长连接负担。

路径：设备 → 应用转发2GB → 对象存储

**基线：授权分块直传对象存储**

服务管理权限与元数据，字节直传；块校验完成后才发布新版本。

路径：设备 → 分块对象上传 → 校验发布

### 扩展瓶颈：小部分文件改变时怎么省流量？

**基线：上传变化块并复用旧块**

稳定分块与内容标识可复用未变化块，但需维护版本到块的映射。

路径：修改块 → 块清单 → 新版本

**备选：每次全量重新上传**

全量传输实现简单，却不利于大文件小修改场景。

路径：完整文件 → 全量传输 → 新版本

### 故障处理：上传中途断线怎么办？

**备选：立即把部分内容标记为完成**

提前发布会让其他设备下载残缺内容。

路径：部分块 → 提前发布 → 残缺文件

**基线：按会话续传并清理残块**

查询成功分块后补传失败块；过期会话残块由后台回收。

路径：断线 → 恢复会话 → 补块后发布


## 适用边界 · 什么时候，需要重新考虑

内容哈希能辅助校验与去重，但不能单独表达权限、目录归属和版本历史。未发布分段要清理，删除标记要保留足够时间供离线设备看到。跨设备同步最终是否覆盖或合并，应是产品明确承诺的一部分。


**本场景下的扩展方向**

上传变化块并复用旧块。稳定分块与内容标识可复用未变化块，但需维护版本到块的映射。

**另一条路径与它的代价**

每次全量重新上传。全量传输实现简单，却不利于大文件小修改场景。


## 带走结论 · 把这几个想法，带走

- 文件字节与版本元数据分离。
- 完整校验后发布，基础版本检查防止静默覆盖。
- 续传解决网络中断，垃圾回收解决未完成上传。
