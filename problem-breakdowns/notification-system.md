通知是一段可追踪的投递流程，渠道接受与用户看到不能合并成一个成功值。

## 遇见问题 · 先从一个具体场景开始

业务事件触发站内信、邮件或推送。渠道可能超时，用户会退订，同一业务事件也可能重复到达。


## 概念原理 · 先把概念讲清楚

- **通知意图**：业务希望发出的逻辑消息，带接收者、模板、业务身份和渠道策略。
- **渠道回执**：外部供应商对投递阶段的反馈，可能延迟、重复或乱序。


业务服务创建通知意图后，由独立流程检查用户偏好、选择渠道并投递。邮件、短信和应用推送有不同限制、费用与失败语义，不能让一个慢渠道阻塞所有通知。持久意图连接业务事件与后续重试，发送记录帮助查询最终发生了什么。


重试需要区分明确失败与结果不确定。供应商已接收但响应丢失时，盲目再次发送可能重复打扰用户。可以使用渠道支持的幂等键或查询外部状态；没有这些能力时，应明确重复风险。回执按消息与阶段版本处理，旧回执不能把已完成状态倒退。


## 图解推导 · 从约束，一步步搭出基线

**需要保存的实体**

Notification、Preference、DeliveryAttempt

**对外接口示例**

POST /notifications；GET /notifications/{id}


### 需求边界 · 先划定边界

不同渠道的确认范围不同，服务接收不能代表用户已经看到。

路径：通知接受 → 渠道处理 → 确认或失败

基线设计 · 已接受、发送中、渠道确认、失败


### 实体与接口 · 把数据和接口连起来

核心实体：Notification、Preference、DeliveryAttempt。接口示例：POST /notifications；GET /notifications/{id}。同人不同事件可分别通知，同事件同渠道重试复用身份。

路径：事件＋用户＋渠道 → 唯一通知 → 投递

基线设计 · 业务事件、收件人、渠道


### 基础架构 · 跑通一条主路径

失败与速率按渠道隔离，邮件变慢不会阻塞站内信。

路径：通知路由 → 渠道队列 → 各适配器

基线设计 · 独立渠道队列与适配器


### 扩展瓶颈 · 沿着瓶颈扩展

有界并发、退避与重要性分级保护渠道配额和用户体验。

路径：优先级队列 → 渠道限速 → 稳定发送

基线设计 · 优先级与速率控制


### 故障处理 · 处理不确定的结果

先查询或依赖服务商去重；不支持时明确可能重复，限制重试并保留记录。

路径：响应超时 → 查询或幂等重试 → 核实

基线设计 · 记录不确定并复用渠道幂等键


## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

订单发货通知N经短信渠道发送，供应商接受后网络断开。系统记录待确认，后续回执到达才推进；用户屏幕是否真正看到通常不可直接保证。偏好取消后排队中的普通营销通知也要再次校验，而不是只在最初创建时检查一次。


## 动手探索 · 现在，亲手改变一个条件

比较持久意图与同步直发，沿回执丢失路径解释“已接收”“已送达”“已读”分别由谁证明。

### 需求边界：先明确哪几种状态？

**备选：接口接受后就标用户已读**

邮箱接收或推送平台确认都不等于阅读。

路径：请求入队 → 标已读 → 错误承诺

**基线：已接受、发送中、渠道确认、失败**

不同渠道的确认范围不同，服务接收不能代表用户已经看到。

路径：通知接受 → 渠道处理 → 确认或失败

### 实体与接口：去重键包含什么？

**基线：业务事件、收件人、渠道**

同人不同事件可分别通知，同事件同渠道重试复用身份。

路径：事件＋用户＋渠道 → 唯一通知 → 投递

**备选：只用收件人ID**

只按收件人会误删该用户后续所有通知。

路径：用户ID → 过度去重 → 后续消息丢失

### 基础架构：多渠道怎样执行？

**备选：一个同步循环发送全部**

同步串行把最快渠道拖到最慢渠道的速度。

路径：邮件等待 → 推送等待 → 整体超时

**基线：独立渠道队列与适配器**

失败与速率按渠道隔离，邮件变慢不会阻塞站内信。

路径：通知路由 → 渠道队列 → 各适配器

### 扩展瓶颈：渠道配额有限又有突发？

**基线：优先级与速率控制**

有界并发、退避与重要性分级保护渠道配额和用户体验。

路径：优先级队列 → 渠道限速 → 稳定发送

**备选：无限并行重试**

过量重试会持续触发限流并扩大积压。

路径：突发重试 → 渠道拒绝 → 更多重试

### 故障处理：服务商已接收但响应超时？

**备选：立刻用新身份无限重发**

超时不证明没发，新身份可能造成重复通知。

路径：超时 → 新身份重发 → 重复送达

**基线：记录不确定并复用渠道幂等键**

先查询或依赖服务商去重；不支持时明确可能重复，限制重试并保留记录。

路径：响应超时 → 查询或幂等重试 → 核实


## 适用边界 · 什么时候，需要重新考虑

通知去重应围绕业务动作，不要按文本相同合并所有消息，否则两次合法订单通知可能被误删。退避、重试上限、死信与人工排查需要明确，避免失败洪峰反复冲击渠道。


**本场景下的扩展方向**

优先级与速率控制。有界并发、退避与重要性分级保护渠道配额和用户体验。

**另一条路径与它的代价**

无限并行重试。过量重试会持续触发限流并扩大积压。


## 带走结论 · 把这几个想法，带走

- 接受、渠道确认和阅读状态分开描述。
- 业务身份支持去重，渠道隔离支持稳定性。
- 退订与权限应在实际发送前再次校验。
