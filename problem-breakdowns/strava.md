轨迹是带时间与顺序的采样序列，活动摘要是经过规则计算的结果。

## 遇见问题 · 先从一个具体场景开始

用户离线记录跑步，结束后上传轨迹并查看路线与分段成绩。GPS会跳点，设备可能重复上传同一活动。


## 概念原理 · 先把概念讲清楚

- **轨迹点**：带位置、采样时间与序号的数据点，需要处理重复、乱序与异常。
- **活动版本**：一次活动处理结果的身份，让重算和修正不会与旧摘要混淆。


运动记录可能在手机上离线累积，重连后分批上传。接口需要活动ID和批次或点身份，让同一批重试不重复追加。原始点保留可重算依据，距离、速度与路线预览是派生结果。把原始数据与摘要分开，规则改变时才能重新计算而不丢事实。


轨迹要按时间与序号整理，识别缺口、重复和明显异常位置。计算相邻点距离后累加，并结合采样间隔估计速度；GPS漂移可能制造虚假运动，过滤策略会改变结果，应保留版本与解释。用户结束活动也不代表全部离线点已经上传。

## 具体例子 · 用一个例子，把因果连起来

### 从条件推到结果

用户跑完后上传两批点，第二批因响应丢失重发。如果直接追加，活动距离可能翻倍；按活动与批次身份去重后只应用一次。若后来补到中间缺失段，摘要可以产生新版本，列表与详情应避免混用新旧计算结果。

### 需求边界：基础功能先包括什么？

**备选：先做全球实时竞速**

实时功能不能弥补活动数据无法可靠保存。

路径：实时广播 → 竞速 → 离线活动缺失

**基线：可靠上传、路线展示、成绩处理**

活动上传与离线恢复先构成闭环，实时竞速有额外延迟约束。

路径：记录轨迹 → 活动上传 → 路线与成绩

### 实体与接口：轨迹点必须保留哪些维度？

**基线：活动ID、序号、时间和坐标**

顺序和时间用于还原路线与速度；同一位置重复经过是合法的。

路径：有序轨迹点 → 路线 → 时间差速度

**备选：只有经纬度去重集合**

去重集合会破坏绕圈与停留信息。

路径：坐标集合 → 无顺序 → 路线丢失

### 基础架构：大轨迹怎样处理？

**备选：上传请求内完成所有分析**

同步分析容易超时并耦合上传吞吐。

路径：上传HTTP → 全部计算 → 长等待

**基线：对象存原始轨迹，异步计算摘要**

原始数据支持重算，Worker生成距离、地图简化与分段匹配。

路径：原始轨迹 → 任务队列 → 活动摘要

### 扩展瓶颈：分段匹配如何缩小范围？

**基线：空间候选再做路径匹配**

地理范围先裁剪，再校验行进方向与覆盖，不只看两个端点。

路径：轨迹范围 → 分段候选 → 精确匹配

**备选：每条活动比对全球全部分段**

全量比较成本随全球分段数增长。

路径：全球分段 → 逐一比较 → 巨大计算

### 故障处理：重传与GPS跳点怎么处理？

**备选：重传算新活动，异常点全信**

重复活动会影响统计，跳点可能造出不真实速度。

路径：重传与跳点 → 直接统计 → 失真成绩

**基线：活动ID幂等并保留质量标记**

重复上传复用活动；异常检测标记质量，保留原始数据供重算。

路径：稳定活动ID → 质量校验 → 可重算成绩


## 适用边界 · 什么时候，需要重新考虑

地图展示与隐私需要分开处理，公开轨迹可能需要隐藏敏感起终点。采样密度、定位误差与距离模型都会影响统计，不能把简化图解当测量设备精度保证。查询原始长轨迹也应分段与按需加载。


**本场景下的扩展方向**

空间候选再做路径匹配。地理范围先裁剪，再校验行进方向与覆盖，不只看两个端点。

**另一条路径与它的代价**

每条活动比对全球全部分段。全量比较成本随全球分段数增长。


## 带走结论 · 把这几个想法，带走

- 轨迹是有序时间序列，不是坐标集合。
- 原始数据与派生摘要分开，处理流程支持重算。
- 位置隐私与公开路线范围需要单独控制。
