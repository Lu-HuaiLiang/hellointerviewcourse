# 逐课内容核对索引

此表将每课的术语、具体例子、边界和互动指引放在一起，便于核对内容是否围绕同一个学习目标。结构检查与浏览器结果见 browser-report.json；字数不是掌握程度或教学质量的证明。

本次重点复核：缓存故障回源放大、队列净消化速度、库存非负仍可超卖、Top K分片前提、CAP承诺边界、视频发布前置条件，以及五篇真实系统文章的事实与教学推演分离。

| 课程 | 核心术语 | 具体例子的起点 | 适用边界 | 互动指引 |
| --- | --- | --- | --- | --- |
| [系统设计，到底在设计什么？](../index.html#lesson/introduction) | 功能需求、非功能约束 | 假设有100人创建短链、10000人点击 | 常见误区是把技术数量当成完整程度 | 先逐步展开“创建与跳转”的路径，再走到热门点击。口头解释：是哪一个约束让缓存出现在图里？如果拿掉它，首先改变的是正确性还是读负载？ |
| [怎样准备，才不是“看过就忘”？](../index.html#lesson/how-to-prepare) | 提取练习、迁移 | 例如读完消息持久化：先解释为什么“发送成功”不能代表“对方已读”；再把聊天换成邮件通知，发现服务接收、渠道接收、用户阅读也不同 | 集中练习同一类题容易让相似措辞产生熟悉感 | 依次展开阅读、补缺口和迁移三条路径。在最后一步选一个你熟悉的产品，把“重复投递”换成它的业务动作，复述一次恢复过程。 |
| [面试框架：先把主线走通](../index.html#lesson/delivery) | 不变量、高层设计 | 以文件上传为例，先约定上传、下载和列表三种行为 | 时间预算应随着问题调整 | 逐步展开框架，在每段路径上指出上一阶段留下的输入。用文件上传例子复述一遍，最后检查“下载”有没有被只讨论上传的方案遗漏。 |
| [核心概念：跟着一条请求学](../index.html#lesson/core-concepts) | 延迟、吞吐量 | 设一次页面请求串行花费：网络80毫秒、应用10毫秒、数据库10毫秒，总计100毫秒 | 平均延迟会掩盖少数非常慢的请求，峰值流量也可能与平均吞吐相差很大 | 沿流程依次观察等待时间、读写特征与复制延迟。把例子中的80毫秒换成5毫秒，再判断数据库优化的相对价值是否改变。 |
| [选工具之前，先说清工作](../index.html#lesson/key-technologies) | 事实来源、派生数据 | 想象一个订单详情页：写入订单后，页面从数据库或缓存读取；发货服务消费订单事件 | 一个产品往往能做多种事情，不能把“Redis只能缓存”或“Kafka等于普通任务队列”当定义 | 展开三条工具路径，给每个框标注“事实”“副本”或“事件”。再想象缓存节点重启，说明哪些数据需要恢复、恢复依据在哪。 |
| [模式：认出题目背后的形状](../index.html#lesson/patterns) | 争用、扇出 | 一名用户发布一条动态，若有100个关注者，写时扇出大约产生100条收件箱引用；若有100万关注者，同一种模式会把一次发布变成巨大任务 | 常见错误是识别出关键词就照搬完整架构 | 依次展开争用、异步和扇出。在每一步说出它减少了哪种困难、增加了什么成本，再把它对应到你用过的一款产品。 |
| [案例怎么学：不要背架构图](../index.html#lesson/problem-breakdowns) | 基线方案、反例 | 以短链接为例，先完成按短码跳转 | 本教材的品牌案例用于原创设计推演，不代表公司的内部部署 | 在案例路径中从需求走到故障，直接阅读基线后切换一个备选。先指出被改变的承诺，再判断是否能通过放宽需求使它成立。 |
| [网络：一次请求为什么要等？](../index.html#lesson/networking-essentials) | RTT、连接复用 | 假设跨地域RTT为150毫秒，在简化串行模型里多一次往返就多约150毫秒 | HTTP版本、TLS恢复、代理和网络状态会影响具体行为 | 展开首次连接与连接复用，再切到跨地域路径。指出哪些节点能够靠近用户、哪些写入仍需回到权威存储，解释为什么。 |
| [API：先约定彼此怎么说话](../index.html#lesson/api-design) | 幂等键、游标分页 | 假设列表按 created_at 降序，第一页取20条 | 不要把HTTP方法的语义与业务实现混为一谈 | 逐步展开资源、幂等键与分页。沿同一订单ID模拟“响应丢失后重试”，指出去重状态应该在哪个持久边界内写入。 |
| [数据建模：从“怎么读”倒推](../index.html#lesson/data-modeling) | 主键、反规范化 | 设订单行保存 product_id 和 price_at_purchase | 无界数组会让单条记录随时间膨胀：把用户所有消息放在一行里，后续更新和分页都会困难 | 展开实体、查询布局和增长路径。拿订单列表逐项指出哪些字段是历史事实、哪些是当前状态，再解释它们为什么不能统一刷新。 |
| [缓存：让数据库喘口气](../index.html#lesson/caching) | 命中与回源、TTL | 假设每秒1000次读取，90%命中时数据库承受100次；失效后变成1000次，是平时的10倍 | 高命中率不证明数据正确 | 把命中率依次调成0%、90%、100%，每次发送一批请求；然后模拟缓存失效。比较本批与累计数据，解释为什么100%命中配置在故障时仍会全部回源。 |
| [分片：把数据分到不同桌上](../index.html#lesson/sharding) | 分片键、热点键 | 实验中有12个键，每键10次读取，3片时每片40次 | 平均分布会掩盖最忙分片，监控应看每片负载、存储和尾延迟 | 在均匀流量和热点之间切换，再改变分片数与热点读取量。观察最忙分片，解释“增加节点”和“拆分热键”是两件不同的事。 |
| [一致性哈希：加机器时少搬一点](../index.html#lesson/consistent-hashing) | 哈希环、虚拟节点 | 环实验有12个固定键，初始A、B、C位于0°、120°、240° | 少量节点在环上的间距可能不均，虚拟节点能改善区间分摊，但无法保证热键访问均衡 | 加入D并观察橙色键，再回到三节点。沿顺时针为任意一个键找负责人，说明如果D宕机，仅修改路由还缺少哪一步数据恢复。 |
| [CAP：断网时，先承诺哪件事？](../index.html#lesson/cap-theorem) | 线性一致性、分区下的可用性 | 实验用A、B两个余额副本演示，初始都是100 | CAP不是讨论所有延迟、新鲜度与持久性的万能公式 | 先断网，分别执行两种策略下的写入，再恢复网络。说清每次响应意味着什么，并指出为何“返回了错误”不等于CAP所说的可用。 |
| [索引：先缩小你要翻的书页](../index.html#lesson/db-indexing) | 联合索引、选择性 | 订单按用户列最近记录，可考虑(user_id, created_at, id)索引 | 联合索引并非任何情况下都只能使用最左字段，具体优化器可能有其他策略；课程的规则用于理解通常的连续查找路径 | 依次展开全表、联合索引与写入代价。把例子的条件从“某用户最近订单”改成“全站某天订单”，指出原先连续区间为何不再相同。 |
| [数量级：算到能做决定就够](../index.html#lesson/numbers-to-know) | 平均与峰值、并发在途量 | 假设每天8640万次请求，平均1000次/秒；峰值为平均的5倍，则按5000次/秒讨论 | 不要把网上一个延迟数字当生产保证 | 展开平均、峰值和内存三步，每次检查单位。将峰值系数翻倍，重新判断连接数和内存中哪一项随它增长，哪一项并不直接增长。 |
| [Redis：快，也要想清楚会丢什么](../index.html#lesson/redis) | 淘汰、持久化 | 排行榜可以用有序集合维护成员分数，读取前20名而非拉取所有成员后排序 | 常见误区是把快等同于可靠，或把每个查询改成一个很大的脚本以求原子 | 展开结构、淘汰和重启。给排行榜中“展示名次”与“积分账本”分别标注可否重建，观察节点重启对两者的含义。 |
| [Elasticsearch：先找到包含词的文档](../index.html#lesson/elasticsearch) | 倒排索引、近实时 | 用户发帖后按ID能读到，却暂时搜不到，并不一定是写丢了：主存储与搜索可见性有不同边界 | 分片、分词与相关性参数要用实际语料评估 | 依次展开索引建立、写入可见性和业务修改。沿“已删除但仍在候选里”的帖子走一遍，找出最终过滤应该发生在哪。 |
| [Kafka：消息读过，还能再读](../index.html#lesson/kafka) | 分区与偏移量、消费组 | 设日志有偏移0至99，发货组读到80，报表组读到60 | 消费者落后时要同时观察落后数量、时间和保留窗口 | 先比较两个消费组的读取路径，再在速率实验中让生产持续超过消费。解释为什么积压能暂存，却不能让处理能力凭空增加。 |
| [API Gateway：入口该管什么？](../index.html#lesson/api-gateway) | 入口治理、故障域 | 假设创建订单在数据库提交后200毫秒返回，而网关在150毫秒超时 | 网关不应成为聚合全部业务逻辑的巨型服务 | 展开入口职责、入口故障和业务边界，沿创建订单超时的例子指出哪个组件能确定订单是否提交。 |
| [Cassandra：把查询写进主键里](../index.html#lesson/cassandra) | 分区键、压实 | 设每个频道每天一个桶 | 一致性级别规定读写等待哪些副本，不等于所有操作天然线性一致 | 展开分区、文件合并与副本读取。把“查某频道今天”改成“查某用户所有频道发言”，解释为什么原来的主键不够。 |
| [DynamoDB：一次查询应落在哪里？](../index.html#lesson/dynamodb) | 分区键与排序键、条件写入 | 假设任务记录包含version=7 | 不要用无条件覆盖替代并发控制，也不要把索引看成实时复制的免费视图 | 沿主键查询到新增索引，再观察条件更新路径。让两个请求持有同一旧版本，解释失败者为什么需要重新读取而不是盲目覆盖。 |
| [PostgreSQL：先把不变量守住](../index.html#lesson/postgres) | MVCC、条件更新 | 库存为1时，两位买家各执行UPDATE stock SET n=n-1 WHERE n>0，并以是否更新到一行为准 | 事务不能直接把数据库提交和外部邮件发送一起回滚 | 展开事务、并发旧值和冲突恢复。沿库存算例复述两种执行交错，明确成功必须以数据库返回的更新结果判断。 |
| [Flink：迟到的数据怎么算？](../index.html#lesson/flink) | 事件时间、水位线 | 某点击在12:00:58发生，12:01:05才收到 | 水位线不会纠正设备时钟错误，也不能替业务定义有效点击 | 展开事件时间、水位线与恢复路径。把同一事件分别放在允许迟到窗口内外，说明两种结果应怎样向报表解释。 |
| [ZooKeeper：谁现在有资格当领导？](../index.html#lesson/zookeeper) | 租约与会话、栅栏令牌 | A持有任期41，暂停后会话过期；B接任42并成功写入 | ZooKeeper不是用来存海量业务对象的通用数据库 | 展开会话失效与旧领导路径。用任期41和42说明：为什么新主出现后，旧主仍可能运行，以及最终在哪一层拒绝它。 |
| [实时更新：谁主动开口？](../index.html#lesson/realtime-updates) | 轮询与推送、恢复游标 | 聊天室收到消息序号100后断线，服务器期间产生101至105 | “实时”应落实为延迟目标和积压策略 | 比较轮询、推送和重连三条路径。沿100到106的例子指出哪些消息可能重复，哪些可能乱序，并说明稳定序号的作用。 |
| [并发竞争：最后一张票归谁？](../index.html#lesson/dealing-with-contention) | 原子性、乐观并发控制 | 实验初始库存1 | 不要只依赖按钮禁用、单台应用内存锁或“请求一般不会同时到” | 分别推进两种库存模式的两个步骤，再重置。观察“库存记录”和“承诺给买家”两个数字，解释为何只监控前者会漏掉错误。 |
| [多步骤流程：失败后从哪里接上？](../index.html#lesson/multi-step-processes) | 状态机、Outbox | 订单O已付款，发货调用超时 | 补偿不等于时间倒流：已发邮件无法让用户没看过，汇率或库存也可能已经变化 | 沿状态机、补偿与Outbox路径展开。把故障放在“数据库提交后、消息发送前”，指出恢复程序依据哪条持久记录继续。 |
| [扩展读取：少做，近做，分开做](../index.html#lesson/scaling-reads) | 读副本、物化视图 | 一个订单列表每次都聚合1000条明细计算总价，可以先把确定的订单总价保存为业务事实或派生汇总 | 缓存与副本都不能修复低效或无界查询 | 逐步展开缓存、副本与预计算。为“刚修改头像”和“浏览一年前订单”分别选择可接受的新鲜度，并解释是否需要同一读取路径。 |
| [扩展写入：队列能买来多少时间？](../index.html#lesson/scaling-writes) | 积压、背压 | 每秒到达1000个任务，一个Worker处理600个，每秒积压400个，10秒后是4000个 | 积压数之外还要看最老任务年龄：1000个昂贵任务与1000个轻任务意义不同 | 保持默认到达率运行10秒，再增加到两个Worker并继续。最后把到达率调到0或把处理能力调到0，观察积压守恒与恢复边界。 |
| [大文件：字节和元数据分开走](../index.html#lesson/large-blobs) | 分段上传、元数据 | 假设1GB文件分成10段，第7段上传失败 | 多段校验、内容校验、病毒检查和权限撤销是不同责任，不要把某个存储返回标识一概当完整文件哈希 | 沿直传、分段与清理展开。模拟第7段失败，说明哪些记录要保留、哪些请求可重试，以及哪个动作使文件真正可见。 |
| [长任务：接受请求，不等于做完](../index.html#lesson/long-running-tasks) | 任务租约、任务终态 | 导出任务T由A领取，A写完临时文件后暂停，租约到期B重试 | 租约超时不能证明旧进程已停止，取消也不能凭界面按钮立即撤销外部副作用 | 展开任务身份、租约与恢复，再增加到达速率观察等待。说明为什么队列中任务少也不代表没有卡住的执行者。 |
| [短链接：从一次跳转开始](../index.html#lesson/bitly) | 短码、跳转响应 | 假设每天100万次创建、1亿次跳转，粗看读写比100:1 | 不要把编码当加密，连续短码可能被枚举 | 沿五个阶段阅读基线，再切换跳转路径。指出新增统计依赖会影响哪条核心行为，并解释删除要求如何改变缓存选择。 |
| [文件同步：先传字节，再发布版本](../index.html#lesson/dropbox) | 文件版本、同步游标 | A离线修改报告，B在线修改同一路径并发布新版 | 内容哈希能辅助校验与去重，但不能单独表达权限、目录归属和版本历史 | 切换完整发布与提前可见两条路径，再推演旧版本提交。说出在哪一步能保证下载者只看到完整版本。 |
| [即时配送：库存、订单与履约](../index.html#lesson/gopuff) | 预留库存、履约状态 | 某门店还有2盒牛奶，三个订单同时请求 | 展示库存可以允许短暂延迟，确认承诺不应依赖陈旧缓存 | 沿预留、支付和履约路径，切换一个失败方案。指出重复取消会在哪个环节被识别，为什么补偿也需要稳定身份。 |
| [抢票：两个人，一张座位](../index.html#lesson/ticketmaster) | 座位预留、条件状态转移 | 座位A12只剩一张，两位买家同时看到绿色座位图 | 到期不是由客户端倒计时单方面决定，服务端要用一致的时间与状态规则判断 | 先观察浏览和确认的边界，再运行两种库存模式。把故障放在预留到期与支付回执之间，解释为什么需要订单状态协同。 |
| [动态流：发布时写，还是读取时算？](../index.html#lesson/fb-news-feed) | 写时扇出、读时合并 | 普通作者有100个关注者，发布一次写100条引用尚可；大作者有100万关注者，同样做法会产生很大扇出 | 混合模式不是免费的最优解，会增加路径、缓存与去重复杂度 | 比较写时与读时路径，给普通作者和大作者分别计数。指出哪些写入工作因读时合并而不再为沉默用户执行。 |
